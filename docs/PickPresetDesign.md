## 0. 구현 중 설계와 달라진 점

- **4절의 "사용자 행을 잠근 뒤 개수를 센다"를 그대로 따랐다.** 처음에는 자식 테이블을
  세면서 잠그는 방식(`SELECT COUNT(*) ... FOR UPDATE`)으로 구현했는데, 동시 20건 시험에서
  **12건이 저장**됐다 — 그 방식은 이미 있는 행만 잠그고 새 INSERT를 막지 못한다. 설계가
  제시한 대로 `users` 행을 잠그도록 바꿨고 그 뒤 통과한다(DecisionLog D-040).
- **경쟁 테스트를 여러 판 돌린다.** 한 판으로는 타이밍에 따라 놓친다 — 잠금을 뺀 채
  한 판만 돌렸을 때 통과한 적이 있어 5판 × 24요청으로 늘렸다.
- **10절의 "새 실행 경로의 추가 조회를 별도 예산으로 문서화"**: 빠른 픽 실행은 14건으로
  고정했고, 기존 `PickQueryBudgetTest`의 7/12는 그대로 통과한다.
- **6절의 "유효 제외 50 초과 시 409"**: 상한을 넘으면 자르지 않고 멈춘다. 자르면 사용자가
  빼 두라고 한 태그가 조용히 다시 들어와 추천된다.
- 거리 값은 설계대로 300/500/1000/2000만 저장한다. 수동 화면의 자유 거리는 저장할 때
  가장 가까운 단계로 맞추고 **무엇으로 저장되는지 화면에 보여준다**(조용히 바꾸지 않는다).

## 1. 결정과 근거

다음 기능은 인증 사용자가 자주 쓰는 픽 조건을 이름 붙여 서버에 저장하고 다시 실행하는
**상황별 빠른 픽**이다. 예: `회사 점심`, `비 오는 날`, `가볍게`.

저장형 프리셋을 먼저 만드는 이유는 현재 `PickPage`에 카테고리·포함 태그·제외 태그·거리 조건이
이미 있고, 사용자가 매번 같은 조건을 다시 고르는 마찰을 기존 추천 경로를 재사용해 줄일 수 있기
때문이다. 이는 저장소의 화면·API·로드맵을 바탕으로 한 제품 가설이며 사용자 조사 결과는 아니다.

대안은 이번 MVP에서 제외한다. 그룹 투표는 초대·멤버십·동시성·악용 방지와 네트워크 효과가
먼저 필요하고, AI 추천은 개인별 학습 표본과 비교 KPI가 부족하다. 식사 캘린더는 즉시 픽의 반복
입력보다 후순위이며 외부 가져오기·소셜 공유·푸시 알림은 별도 개인정보·권한 설계가 필요하다.

## 2. MVP 범위와 불변식

- 인증 사용자별 서버 저장 프리셋은 최대 10개다.
- 프리셋 선택은 조건을 미리 보여줄 뿐 자동 실행하지 않는다.
- 프리셋 실행에는 조건 덮어쓰기를 허용하지 않는다.
- 저장 조건은 카테고리, 포함 태그, 추가 제외 태그, 최대 거리뿐이다.
- 좌표·장소는 저장하지 않는다. `userId`는 클라이언트 저장 DTO로 받지 않고 인증 주체에서 얻어
  소유자 FK로만 저장한다.
- 기본 제외 태그는 저장 시 복사하지 않고 실행할 때마다 최신 값을 합친다.
- 프리셋은 기본 제외 태그를 해제하거나 덮어쓸 수 없다.
- 태그 삭제로 조건이 사라지면 조용히 넓어진 추천을 실행하지 않는다.
- 건강상 안전을 보증하지 않는다. 결과는 사용자가 직접 붙인 태그의 정확성에만 의존한다.
- 일반 `POST /api/v1/pick` 계약과 null/빈 배열 의미는 바꾸지 않는다.

## 3. 저장 모델

`pick_presets` 부모는 `id BIGINT` PK, `user_id BIGINT NOT NULL`(users FK CASCADE),
`name VARCHAR(30) NOT NULL`, `needs_review TINYINT(1) DEFAULT 0`, `version BIGINT DEFAULT 0`,
`max_distance INT NULL`, 기존 규칙의 생성·수정 시각을 가진다. 최대 거리는 null 또는
300·500·1000·2000만 허용한다. `UNIQUE(user_id, name)`으로 사용자 안에서 유일하게 한다.

이름 비교는 DB의 실제 collation을 따른다. 현재 기본 `utf8mb4_unicode_ci`라면 대소문자를 구분하지
않는 유일성임을 API 문서와 테스트에 고정한다. 이름은 서버에서 trim한 뒤 1~30자여야 한다.

`pick_preset_categories`는 `preset_id`(부모 FK CASCADE), `category VARCHAR(20)`을 가지며
PK 또는 UNIQUE는 `(preset_id, category)`다.

`pick_preset_tags`는 `preset_id`(부모 FK CASCADE), `tag_id`(tags FK CASCADE),
`filter_type VARCHAR(10)`을 가진다. 타입은 `INCLUDE|EXCLUDE`, UNIQUE는
`(preset_id, tag_id, filter_type)`다.

새 Flyway 파일은 구현 시점에 `src/main/resources/db/migration`과 최신 원격 브랜치를 다시 확인해
**다음 미사용 버전**으로 만든다. 현재 보이는 마지막 번호만 보고 `V13`이라고 가정하지 않는다.
적용된 migration은 주석도 수정하지 않는 기존 규칙을 지킨다.

## 4. 입력 검증

생성·수정 DTO의 전체 조건은 다음과 같다.

- `name`: trim 후 1~30자
- `categories`: trim·중복 제거, 최대 20개, 각 값 1~20자
- `includeTagIds`: 최대 20개
- `additionalExcludeTagIds`: 최대 20개
- 모든 태그 ID: 양수, non-null, 현재 인증 사용자 소유이며 존재해야 함
- 포함과 추가 제외의 직접 교집합: 400
- `maxDistance`: `null`, 300, 500, 1000, 2000 중 하나

태그 ID는 중복 제거 후 소유 태그 조회 수와 비교한다. 타인 소유 또는 존재하지 않는 태그는
리소스 존재를 노출하지 않도록 404로 응답한다. 카테고리는 기존 `PickService` 및 메뉴 저장 경로와
동일하게 정규화한다.

동일 이름 생성은 DB UNIQUE 위반까지 잡아 전용 409로 변환한다. 최대 10개 검사는 단순
count-then-insert 경쟁 상태를 허용하지 않는다. 사용자 행을 DB에서 잠근 뒤 개수를 세고 생성하거나,
동등하게 상한을 직렬화하는 제한된 대안을 사용하고 동시 생성 테스트로 10개를 넘지 않음을 증명한다.

## 5. API

기본 경로는 `/api/v1/pick/presets`다.

- `GET /pick/presets`: 내 목록, 최대 10개, 조건을 배치 조회하여 N+1 금지
- `GET /pick/presets/{id}`: 내 단건 상세
- `POST /pick/presets`: 생성, 성공 시 201
- `PUT /pick/presets/{id}`: `version`을 포함한 전체 교체. 검토 복구 시
  `acknowledgeRemovedTags=true` 필수
- `DELETE /pick/presets/{id}?version={version}`: 기존 관례에 맞춘 낙관적 삭제
- `POST /pick/presets/{id}/pick`: 저장 조건으로 즉시 픽

목록·상세 응답에는 `id`, `name`, `categories`, `includeTagIds`,
`additionalExcludeTagIds`, `maxDistance`, `needsReview`, `version`, 생성·수정 시각을 담는다.
저장 DTO나 응답에 좌표, 장소, `userId`를 넣지 않는다.

모든 조회와 변경은 인증 사용자 범위로 찾는다. 타인 프리셋과 없는 프리셋은 같은 404다.
수정·삭제의 오래된 버전은 기존 `VersionGuard`/`CONCURRENT_MODIFICATION` 관례의 409다.
실행은 조회 행위이므로 성공해도 프리셋 버전을 증가시키지 않는다.

오류는 프리셋 없음 404, 이름 중복·10개 상한·오래된 버전·검토 필요 409로 분류한다. 실행 시
유효 제외 상한 또는 기본 제외/포함 충돌도 행동 안내가 있는 409다. DTO 형식·직접 포함/추가 제외
충돌·좌표 조합 오류는 400이다.

## 6. 전용 실행 계약

실행 요청 본문에는 필수 `version`과 선택 `latitude`, `longitude`만 허용한다. 카테고리나 태그 등
필터 override는 받지 않는다. 프리셋 실행은 다음 순서를 하나의 서버 서비스에서 수행한다.

1. 소유자 범위로 프리셋과 조건을 읽는다.
2. 요청 `version`이 현재 버전인지 확인한다.
3. `needsReview=true`면 409로 중단한다.
4. 참조 태그가 여전히 모두 현재 사용자 소유인지 확인한다.
5. 최신 기본 제외 태그를 정확히 한 번 읽는다.
6. 최신 기본 제외와 `additionalExcludeTagIds`를 union·dedupe한다.
7. 유효 제외 태그와 포함 태그가 겹치면 409로 중단한다.
8. 유효 제외 태그가 50개를 넘으면 자르지 않고 행동 안내가 있는 409로 중단한다.
9. 신뢰할 수 있는 `PickRequest`를 조립해 기존 `PickService`를 HTTP가 아닌 내부 호출한다.

실행은 히스토리를 저장하므로 writable transaction이어야 한다. 실행 시 버전 확인은 read/use
의미이며 단독으로 동시 변경과 태그 무효화에 대한 선형화를 보장하지 않는다. lost update나 검토
우회가 없도록 DB locking 또는 동등한 version guard를 적용하고 경쟁 테스트로 증명한다.

프리셋 실행의 최대 히스토리 조건 수는 카테고리 20 + 포함 20 + 유효 제외 50 + 거리 1 = 91이다.
일반 PickRequest의 명시적 제외 최대 20 제한은 그대로 둔다. 전용 실행 경로가 검증한 합성 요청만
최대 50을 허용하며 일반 `POST /pick` 검증을 느슨하게 만들지 않는다.

합성 `PickRequest.excludeTagIds`에는 완성된 유효 제외 집합을 명시적으로 넣는다. 그러면 기존
`PickService`의 `excludeTagIds == null`일 때만 기본값을 조회하는 규칙 때문에 기본 제외를 다시
읽지 않는다. 히스토리에는 실제 적용된 최신 제외 조건이 기록된다.

실행 응답은 기존 픽 결과와 함께 서버가 실제 적용한 유효 필터를 반환한다. 미리보기 뒤 기본 제외가
바뀌어도 서버 결과가 권위 있는 값이며 UI는 이 값으로 실제 제외 조건을 보여준다.

`maxDistance != null`이면 최신 위도·경도가 모두 필요하다. 하나라도 없으면 400이며 거리 없는
픽으로 조용히 폴백하지 않는다. `maxDistance == null`일 때 좌표를 받지 않는 계약으로 고정한다.
검증 실패 시 히스토리는 생기지 않고, 성공 시 정확히 하나만 생겨야 한다.

## 7. 태그 삭제와 검토 복구

`TagService.deleteTag`는 같은 트랜잭션에서 태그 삭제 전에 해당 태그를 참조하는 모든 프리셋을
벌크 갱신한다.

- `needs_review = true`
- `version = version + 1`
- `updated_at` 갱신

한 프리셋은 한 번만 갱신한다. 그다음 기존 `menu_tags` 정리를 하고 태그를 삭제한다. 자식 FK
cascade가 프리셋 태그 행을 제거하지만 부모 프리셋은 남는다. UI는 살아남은 조건과 일반 경고를
보여준다. 삭제된 태그 이름을 별도 보존하지 않으므로 이번 MVP는 정확히 어떤 태그였는지 표시하지
않는다.

검토 상태는 편집 화면에서 현재 전체 조건을 명시적으로 다시 저장해야만 해제된다. 이때 PUT은
`acknowledgeRemovedTags=true`를 요구한다. 수정 서비스는 이 승인과 태그 소유권·상한·충돌·현재
버전을 모두 검증한 뒤에만 `needsReview=false`로 만든다. 삭제된 ID가 남은 오래된 요청은 404이며
검토 상태를 해제하지 않는다. 태그 삭제 뒤 조건이 줄었다는 이유로 실행을 자동 허용하지 않는다.

## 8. 계정 삭제와 개인정보

프리셋은 개인 선호 정보이며 알레르기·기피·종교적 식습관을 추론할 여지가 있다. 요청 본문,
프리셋 이름, 태그 이름을 로그에 남기지 않고 모든 쿼리를 인증 사용자로 제한한다.

탈퇴의 기존 30일 soft-delete 유예 동안 프리셋도 복구 대상 데이터로 유지한다. 유예가 끝난 hard
purge에는 프리셋 자식과 부모 정리를 명시적으로 포함하고 `UserHardDeleteServiceTest`로 다른 사용자
데이터를 건드리지 않으면서 모두 삭제됨을 증명한다. FK cascade가 있어도 수동 purge 목록 누락을
방치하지 않는다.

위치 좌표는 실행 순간 거리 계산에만 사용한다. DB, 애플리케이션 로그, URL, localStorage에 저장하지
않는다. 기존 `PrivacyReview.md`의 “좌표 비영속” 약속을 유지한다.

## 9. 프론트엔드 상호작용

빠른 픽은 기존 수동 필터와 구분되는 별도 모드로 제공한다. 프리셋을 선택하면 이름, 저장 조건,
현재 기본 제외가 실행 때 추가된다는 안내를 먼저 보여주고 사용자가 실행 버튼을 눌러야 한다.

프리셋 필드를 하나라도 편집하면 활성 프리셋 모드를 종료하고 기존 수동 draft로 전환한다.
“수동 조건으로 전환됨” 배너를 보여주며 저장된 프리셋을 암묵적으로 덮어쓰지 않는다.

수동 조건을 프리셋으로 저장할 때 추가 제외는 `현재 제외 선택 - 최신 기본 제외`다. 사용자가 기본
제외를 의도적으로 빼 둔 수동 상태라면 프리셋이 그 override를 저장할 수 없음을 설명하고,
기본값을 다시 적용하거나 저장을 취소하도록 한다. 조건을 조용히 바꾸지 않는다.

거리 프리셋은 실행 버튼을 누른 뒤 브라우저에서 매번 새 위치를 요청한다. 거부·시간초과·오래된
콜백이면 실행하지 않고 거리 조건을 끈 프리셋으로 편집하는 명시적 선택지를 준다. 기존 PickPage의
generation guard와 같은 방식으로 껐다 켠 요청의 늦은 콜백을 무효화한다.

저장·실행 pending 동안 중복 제출을 막고, 오류는 해당 컨트롤 가까이 행동 가능한 문장으로 알린다.
선택·저장·삭제·실행 후 초점 이동, `aria-live`, 키보드 조작, `prefers-reduced-motion` 관례를 기존
PickPage 수준으로 유지한다. 기본 제외는 실행 직전 바뀔 수 있고 결과의 실제 조건이 최종임을 알린다.

## 10. 구현 경로와 성능 경계

백엔드는 `domain/pick` 아래 preset entity/repository/service/controller/DTO를 추가하고,
`TagService`, `UserHardDeleteService`, 관련 repository와 테스트를 최소 범위로 확장한다.
프론트엔드는 `frontend/src/api/pickPresets.ts`, `PickPage`와 전용 테스트를 추가한다.

기존 일반 PickService hot path를 바꾸거나 복제하지 않는다. 현재 작업 트리에는 픽 최적화 변경이 있고,
상류에는 query-budget PR #246/#247 결과가 있으므로 원격 main 통합 전에 최신 상태만 대조한다.
현재 사용자 미커밋 변경을 덮어쓰거나 복붙하지 않고, 동일 최적화가 이미 상류에 반영됐는지 확인한다.
새 프리셋 실행의 추가 조회는 별도 테스트 예산으로 문서화하고
기존 `PickQueryBudgetTest`의 7/12 SELECT fixture를 깨지 않는다. 측정 없이 운영 성능 개선을 주장하지
않는다.

## 11. 검증 기준

백엔드 단위·통합 테스트는 CRUD, 소유권 404, 이름 정규화·중복, 10개 제한 동시 생성,
수정·삭제·실행 버전 충돌을 덮는다. 태그 삭제 검토 표시·버전 증가·cascade·실행 차단과 전체
교체 후 복구, hard purge 격리도 검증한다. 카테고리·태그 검증, 최신 기본 제외 union 50 성공과
51 실패, 새 기본 제외/포함 충돌, 거리 좌표 누락·부분 입력·비저장을 포함한다. 거절 시 히스토리
0개, 성공 시 정확히 1개와 실제 조건 snapshot, 목록 batch 조회와 실행 쿼리 예산을 고정한다.

프론트 Vitest와 E2E는 수동 조건 저장→새로고침 복구→미리보기→명시 실행, 태그 삭제 경고→실행
차단→확인 저장→재실행을 덮는다. 기본 제외 최신값과 서버 실제 조건, 위치 거절·시간초과·늦은
콜백, 수동 draft 전환, pending·오류·초점·키보드·스크린리더 상태도 검증한다.

구현 완료 확인 명령은 `gradlew check`, 프론트 lint/build/test/e2e 전체다. 환경 의존 E2E가 있다면
필요 조건과 미실행 사유를 정확히 남긴다.

## 12. 문서와 전달 경계

구현 담당자는 실제 구현 상태에 맞춰서만 `Specification.md`, `Planning.md`의 API·ERD,
`PrivacyReview.md`, `CurrentStatus.md`, `DecisionLog.md`를 갱신한다. 설계만 존재하는 동안 완료로
표시하지 않는다.

이 인계는 push, 배포, SMTP/JWT/SSH 설정 변경, 보안 정책 변경을 승인하지 않는다. commit/PR은
구현 담당자의 대화에서 사용자가 별도로 승인한 경우에만 수행한다. 현재 작업 트리의 기존 dirty
변경과 `debug.log`를 기능 커밋에 통째로 포함하지 않는다.

향후 범위는 그룹·소셜 픽, 식사 캘린더, AI 개인화, 외부 가져오기, 공유, 푸시 알림이다. 각 항목은
이 MVP의 테이블이나 API에 미리 끼워 넣지 않고 별도 제품 검증 후 설계한다.
