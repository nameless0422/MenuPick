# 방문 캘린더 설계

**작성일: 2026-09-15 / 상태: 구현·검증 완료, 미커밋·미PR·미배포**

## 1. 목적과 의미

히스토리 목록을 바꾸지 않고, 사용자가 방문 처리한 기록을 월 단위로 돌아보는 캘린더를
추가한다. 캘린더의 날짜는 실제 식사일이나 방문일을 뜻하지 않는다. 정확한 문구는
**‘방문했어요를 누른 날짜’**이며, 현재 저장된 `visitedAt`의 의미를 그대로 보여준다.

실제 방문 날짜를 사용자가 별도로 입력·수정하는 기능은 후속 개선 후보이며 이번 범위에는
포함하지 않는다.

## 2. 범위

- 인증 사용자의 본인 기록만 월 단위로 읽는다.
- `visited=true`이고 `visitedAt`이 조회 월의 `[monthStart, nextStart)`에 드는 기록만 포함한다.
- 메뉴명·식당명은 기존 히스토리 보존 정책을 따른다. 연결 엔티티가 삭제되어도 히스토리에
  보존된 이름을 반환한다.
- 기존 히스토리 목록, 방문 처리, 삭제 API와 화면 동작은 변경하지 않는다.
- 조회 시 위치 좌표나 픽 필터 조건을 받거나 반환하지 않으며 외부 API도 호출하지 않는다.
- 읽기 전용 기능이며 신규 테이블·컬럼·인덱스와 Flyway 마이그레이션은 없다.

## 3. API 계약

`GET /api/v1/history/calendar?month=YYYY-MM`은 인증이 필요하다.

- `month` 생략: KST(`Asia/Seoul`) 기준 현재 월
- 허용 범위: `2000-01` 이상, KST 현재 월 이하
- 형식 오류·2000-01 이전·미래 월: `400 Bad Request`
- 선택·정렬: repository는 `visitedAt DESC, id DESC`로 최대 501건을 조회한다. 서비스는
  그중 최신 500건을 선택한 뒤 뒤집어 API 응답을 `visitedAt ASC, id ASC`로 반환한다.
- 제한: 501번째 행이 있으면 `truncated=true`; 그렇지 않으면 `false`. 따라서 잘린 응답은
  월초 500건이 아니라 **해당 월의 최근 500건**이다.
- 정상 빈 결과도 `200 OK`

응답 DTO의 data는 다음 모양이다.

```json
{
  "month": "2026-09",
  "entries": [
    {
      "id": 123,
      "menuName": "김치찌개",
      "restaurantName": "우리식당",
      "visitedAt": "2026-09-15T12:34:56"
    }
  ],
  "truncated": false
}
```

`menuName`과 `restaurantName`은 기존 히스토리 정책상 값이 없을 수 있다. 서버는 사용자
식별자를 요청값으로 받지 않고 인증 주체에서 얻으며, repository 조건에도 소유 사용자를
포함한다.

## 4. 시간과 화면

월 경계는 KST의 해당 월 1일 00:00과 다음 달 1일 00:00으로 계산한다. DB의
`LocalDateTime` 계약을 유지하며 프론트는 ISO local datetime의 날짜 부분(`YYYY-MM-DD`)을
문자열로 잘라 같은 날짜의 항목을 묶는다. 브라우저 timezone이나 `Date` 변환으로 날짜를
다시 해석하지 않는다.

화면은 이전 달·다음 달 탐색과 월 표시를 제공한다. 다음 달 버튼은 KST 현재 월에서
비활성화하고, 2000년 1월 이전으로 이동하지 못하게 한다. 캘린더는 CSS 배치만으로 의미를
표현하지 않고 요일 헤더와 날짜 셀을 갖는 semantic `table`을 사용한다. 빈 날짜, 로딩,
오류, 빈 월, 500건 초과 안내가 보조기술에서도 구분되게 한다. `truncated=true`이면
**‘최근 500개만 표시해요’**라고 알려 실제 선택 규칙과 문구를 일치시킨다.

## 5. 보안·개인정보·성능

- 인증 누락은 기존 보안 정책대로 처리하며 타인 기록을 조회할 경로를 만들지 않는다.
- 응답에는 캘린더에 필요한 히스토리 ID, 보존 이름, 방문 처리 시각만 포함한다. 좌표,
  필터 조건, 사용자 식별정보는 포함하지 않는다.
- 월 범위와 최대 행 수를 제한해 무제한 이력 조회를 막는다.
- 이름 조회가 항목별 추가 쿼리로 번지지 않도록 projection 또는 fetch join 기반 단일 목록
  조회를 사용하고, 테스트로 query/fan-out 예산을 고정한다.
- 이 조회는 상태를 쓰지 않으며 히스토리의 보존·삭제 정책을 바꾸지 않는다.

## 6. 테스트 행렬

| 영역 | 확인 사항 |
| --- | --- |
| 인증·소유권 | 미인증 거절, 본인 기록만 반환, 타인 기록 혼입 없음 |
| 월 검증 | 생략 시 KST 현재 월, 윤년·연말 경계, 형식 오류, `1999-12`, 미래 월 400 |
| 범위 | `visited=true`만 포함, 시작 경계 포함, 다음 달 시작 제외, null `visitedAt` 제외 |
| 응답 | `visitedAt ASC, id ASC`, nullable 이름, 삭제된 연결 대상의 보존 이름, 빈 월 200 |
| 제한 | 500건 이하 `truncated=false`, 501건 이상 최신 500건을 오름차순 응답·`true` |
| 성능 | 목록 쿼리의 고정 query budget, 행별 이름 조회 fan-out 없음 |
| UI | semantic table, 월 탐색 경계, 로딩·오류·빈 상태, 날짜 substring 그룹화, ‘최근 500개’ 안내 |
| 회귀 | 기존 히스토리 목록·방문 처리·삭제 동작 불변 |
