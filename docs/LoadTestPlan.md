# 부하 테스트 설계

**2026-08-16** — [ImprovementBacklog 12번](ImprovementBacklog.md)의 "부하 테스트 실행"을 위한 설계.
현재 `scripts/k6/load-test.js`는 실행 자체가 막혀 있고(토큰 수동 주입), 실행하더라도 측정이 성립하지 않는다(시드 데이터 없음). 이 문서는 그 둘을 풀고 무엇을 어떤 기준으로 재는지 정한다.

---

## 1. 이 테스트가 답해야 할 질문

**"P95 목표를 만족하는가"가 아니다.** 그건 부하가 낮으면 언제나 예이고, 높으면 언제나 아니오다.

실제로 답해야 할 질문은 **"어디서 꺾이는가"**다. 근거는 설정에 이미 적혀 있다.

| 항목 | 값 | 출처 |
| --- | --- | --- |
| 목표 동시 사용자 | 100명 | [Planning 7.1](Planning.md#71-성능-목표) |
| 톰캣 스레드 | 50 | `application-prod.yml:65` |
| DB 커넥션 풀 | 10 (획득 타임아웃 5초) | `application-prod.yml:14,17` |
| 앱 힙 | ≈1152MB (`mem_limit 1536m` × `MaxRAMPercentage=75`) | `Dockerfile:37`, `docker-compose.prod.yml:140` |

목표 100명이 스레드 50개·커넥션 10개를 통과해야 한다. 요청이 짧으면 문제없이 흐르지만, **커넥션 획득 타임아웃이 5초**라 포화 지점을 넘는 순간 응답은 느려지는 게 아니라 **실패로 꺾인다**. 그 무릎의 위치가 이 테스트의 1차 산출물이다.

산출물은 세 가지다.
1. **무릎 지점** — 몇 VU부터 P95가 목표를 넘고, 몇 VU부터 에러율이 오르는가
2. **1차 병목** — 무릎에서 무엇이 먼저 마르는가 (커넥션 풀 / 톰캣 스레드 / 힙 / MySQL)
3. **메뉴 수 민감도** — 아래 3절 참고. 이게 이 서비스 고유의 성능 축이다

## 2. 측정을 망치는 것 네 가지 — 먼저 무력화한다

### 2.1 픽은 조회가 아니라 쓰기다

`PickService.pick`은 `@Transactional`이고, 성공할 때마다 `histories` 행과 `history_filter_conditions` 행을 쓴다(`PickService.java:41-42, 196-224`). 즉 픽 시나리오는 **쓰기 부하**다.

따라서:
- 픽 P95 목표 500ms에는 INSERT가 포함된다.
- **soak 중 DB가 단조 증가한다.** 20 rps × 1시간 = 히스토리 7.2만 행. MySQL에는 부담이 아니지만, 반복 실행하려면 정리 절차가 필요하고 회차 간 결과를 비교할 때 이전 회차가 남긴 행이 변수가 된다.
- 읽기 전용 시나리오(`GET /menus`, `GET /history`)와 반드시 분리해서 봐야 한다.

### 2.2 픽 비용은 요청이 아니라 **그 사용자의 메뉴 수**에 비례한다

`PickService`는 SQL로 필터링하지 않는다. 사용자의 비제외·미삭제 메뉴를 **전부** 가져온 뒤(`findAllByUserIdAndIsExcludedFalseAndDeletedAtIsNull`, LIMIT 없음) 카테고리·태그·거리를 자바 스트림으로 거른다(`PickService.java:44-49, 68-114`). 게다가 `categories`·`tags`·`menuRestaurants`가 전부 지연 로딩이라, 필터를 타면 후보 수만큼 배치 조회(`default_batch_fetch_size: 100`)가 따라붙는다.

> 이 인메모리 필터링은 이미 의도적 보류다 — 백로그 #16의 "푸시다운은 보류".

**결과: 메뉴 5개인 계정으로 잰 숫자는 메뉴 300개인 계정에 대해 아무것도 말해주지 않는다.** 그래서 시드는 메뉴 수를 명시적으로 고정해야 하고, 테스트는 **최소 두 가지 볼륨**에서 돌려 기울기를 봐야 한다. 이 축을 빼면 "지금은 빠르다"는 결론만 얻고, 사용자가 메뉴를 쌓았을 때 무슨 일이 생기는지는 그대로 모른다.

### 2.3 레이트 리밋이 부하 생성기를 먼저 막는다

| 버킷 | 대상 | 한도 | 키 |
| --- | --- | --- | --- |
| `rl:auth:` | `POST /api/v1/auth/*` (로그인·가입·재발급 등 9개) | 10/분 | IP |
| `rl:demo:` | `GET /api/v1/pick/demo` | 10/분 | IP |
| `rl:proxy:` | `GET /api/v1/{kakao,naver}/*` | 30/분 | IP |

(`RateLimitFilter.java:58-78`, `RateLimitProperties.java:31-34`. 프록시 버킷은 코드상 사용자 키를 쓰도록 준비돼 있으나 필터 등록 순서상 principal이 비어 있어 실제로는 IP로 동작한다 — 백로그에 "필터 순서만 바꾸면 전환"으로 이미 기록됨.)

k6 러너는 IP 하나다. 즉 **인증·데모·프록시 경로는 부하를 걸 수 없다.** 대응은 경로마다 다르다.

- **인증 경로**: 부하 대상에서 뺀다. 대신 토큰을 오프라인 발급한다(4절). 로그인 비용은 별도 시나리오에서 낮은 VU로 따로 잰다(2.4).
- **프록시 경로**: 테스트 환경에서 `RATE_LIMIT_PROXY_PER_MINUTE`를 올리거나, VU마다 다른 `X-Forwarded-For`를 붙인다. 후자가 가능한 이유는 prod/dev가 `trust-proxy: true`, `trusted-proxy-hops: 1`이기 때문이다. **어느 쪽을 골랐는지 결과에 반드시 적는다** — 한도를 올리고 잰 숫자는 운영 설정의 숫자가 아니다.
- **데모 픽**: 게스트 온보딩용이고 DB를 안 탄다. 부하 대상 아님.

### 2.4 로그인은 다른 종류의 비용이다 — 섞지 않는다

Argon2id `m=9216KiB, t=4, p=1` (`SecurityConfig.java:60-77`). 검증 1회에 **9MiB 메모리**를 잡고 수십 ms CPU를 쓴다. 톰캣 스레드 50개가 동시에 로그인을 처리하면 순간 450MB가 힙(≈1152MB)에서 사라진다.

이건 DB나 네트워크가 아니라 **CPU·메모리 병목**이라, 일반 조회와 한 시나리오에 섞으면 두 결과가 서로를 오염시킨다. 별도 시나리오로 낮은 VU에서 따로 잰다. (여기에 계정별 로그인 실패 제한 10회/15분도 걸리므로 — `LoginAttemptLimiter.java:39,42` — 반드시 성공하는 자격증명만 쓴다.)

## 3. 시드 설계

현재 시드 수단이 **하나도 없다**. `CommandLineRunner`도, seed SQL도, `@Profile("local")` 로더도 없다. Flyway 마이그레이션 5개는 전부 DDL이다. `DemoPickService`의 샘플 11종은 하드코딩 상수라 실제 `menus` 행과 무관하다.

### 3.1 볼륨 프로파일

메뉴 수가 성능 축이므로(2.2) 두 개를 고정한다.

| 프로파일 | 사용자 | 사용자당 메뉴 | 사용자당 식당 | 메뉴-식당 링크 | 의도 |
| --- | --- | --- | --- | --- | --- |
| `typical` | 50 | 30 | 15 | 메뉴당 1~2 | 평범한 사용자. 기준선 |
| `heavy` | 10 | 300 | 60 | 메뉴당 2~3 | 인메모리 필터링의 기울기를 드러내는 쪽 |

사용자를 여럿 두는 이유: 한 계정만 쓰면 그 사용자의 메뉴 행이 MySQL 버퍼풀과 하이버네이트 배치 캐시에 완전히 얹혀, 실제보다 좋은 숫자가 나온다. VU가 사용자 풀에서 골라 쓰게 한다.

카테고리·태그는 필터 시나리오가 실제로 걸러지도록 분포를 준다 — 전 메뉴가 같은 카테고리면 필터가 아무것도 안 하고, 아무 메뉴도 안 맞으면 전부 404가 되어 둘 다 측정이 성립하지 않는다.

### 3.2 시드 수단: SQL 직접 삽입

API로 시드하는 방법(인증 CRUD를 호출)도 가능하지만 `heavy` 프로파일이 3,000행이라 느리고, 그 자체가 쓰기 부하라 시드와 측정이 섞인다. **SQL 벌크 삽입**으로 간다.

지켜야 할 제약(V1~V5 스키마):

| 테이블 | NOT NULL | UNIQUE |
| --- | --- | --- |
| `users` | `nickname(50)`, `email_verified` | `email`, **`nickname`** (V5) |
| `menus` | `user_id`, `name(100)`, `is_excluded`, `weight` | 없음 |
| `restaurants` | `user_id`, `name(200)`, `latitude`, `longitude` | `(user_id, kakao_place_id)` (V5) |
| `menu_restaurants` | `menu_id`, `restaurant_id` | `(menu_id, restaurant_id)` |

주의할 지점 세 가지:
- **닉네임이 유니크다(V5).** 시드 닉네임에 인덱스 번호를 붙여 충돌을 피한다.
- **`kakao_place_id`는 NULL로 둔다.** MySQL은 유니크 인덱스에서 NULL을 서로 다른 값으로 보므로 사용자당 식당을 자유롭게 넣을 수 있다.
- **`is_excluded=0`, `deleted_at=NULL`이어야 픽 후보가 된다.** 빠뜨리면 전 요청이 `NO_PICK_CANDIDATES`로 떨어지고, 테스트는 "빠르게 404를 내는 속도"를 재게 된다.

시드 사용자는 `email_verified=1`, `email`은 NULL로 둔다. 로그인시킬 필요가 없기 때문이다(4절). 로그인 시나리오(2.4)용 계정만 별도로 `auth_providers`에 `provider='LOCAL'` + 알려진 비밀번호의 Argon2 해시를 넣는다.

### 3.3 정리

시드와 회차 잔여물(히스토리)을 지우는 teardown이 함께 있어야 한다. 시드 사용자를 알아볼 수 있게 닉네임/이메일에 고정 접두어(`loadtest-`)를 준다.

## 4. 토큰: 오프라인 발급

**이게 이번 설계에서 가장 크게 바뀌는 지점이다.** 기존 스크립트는 브라우저로 실제 소셜 로그인을 해서 `ACCESS_TOKEN`을 복사해 넣으라고 요구했고, 그래서 자동 실행이 불가능했다.

그럴 필요가 없다. Access Token 검증 경로를 보면:

- 토큰 내용은 `sub = userId`, `token_type = "access"`, `iat`, `exp`가 전부다 (`JwtTokenProvider.java:85-94`).
- 서명은 `jwt.secret`에 대한 HMAC-SHA256이다.
- `JwtAuthenticationFilter`는 **서명·만료·`token_type`만 확인한다.** 요청마다 DB나 Redis를 조회하지 않는다 (`JwtAuthenticationFilter.java:33-40`, `JwtTokenProvider.java:96-112`).

즉 `JWT_SECRET`과 사용자 id만 있으면 **k6가 토큰을 스스로 만들 수 있다.** 얻는 것이 세 가지다.

1. OAuth 왕복도, 메일 인증도 필요 없다 → 완전 자동 실행
2. 인증 레이트 리밋(10/분)을 아예 건드리지 않는다
3. 측정에 Argon2 비용이 섞이지 않는다

**만료 30분 문제**: soak(1시간 이상)는 중간에 토큰이 만료돼 전부 401이 된다. 그래서 토큰을 밖에서 한 번 만들어 넘기는 방식으로는 부족하고, **스크립트 안에서 발급**해야 한다. k6의 `k6/crypto`(`hmac('sha256', ..., 'base64rawurl')`)와 `k6/encoding`(`b64encode(..., 'rawurl')`)이면 HS256 JWT를 조립할 수 있다. VU마다 자기 사용자 id로 토큰을 만들고, 주기적으로 재발급한다.

> **안전 조건**: 이 방식은 부하 생성기에 서명 시크릿을 준다는 뜻이다. **운영 시크릿을 이렇게 쓰면 안 된다.** 부하 테스트는 전용 환경에서, 그 환경 전용 `JWT_SECRET`으로만 돌린다. 운영 대상으로 돌려야 한다면 토큰 발급 방식이 아니라 대상 선정을 다시 생각해야 한다.

## 5. 시나리오

k6 executor를 나눠 네 가지로 돌린다. **한 번에 하나씩** 돌린다 — 섞으면 어느 시나리오가 무릎을 만들었는지 알 수 없다.

### 5.1 `smoke` — 배선 확인

1 VU, 1분. 모든 대상 엔드포인트를 한 번씩. **판정: 에러 0건.**
목적은 성능이 아니라 "시드가 제대로 들어갔고 토큰이 먹히는가"다. 여기서 픽이 404를 내면 그 뒤 결과는 전부 무의미하다.

### 5.2 `load` — 목표 부하에서의 상태

목표치인 동시 100명을 `constant-arrival-rate`로 재현한다. `constant-vus`가 아니라 도착률 기준으로 하는 이유: VU 고정은 응답이 느려지면 요청도 같이 느려져(closed-loop) 부하가 저절로 줄어든다. 그러면 포화가 숨는다.

- 읽기: `GET /menus?size=20`, `GET /history?size=20`
- 쓰기: `POST /pick` (필터 없음 / 카테고리 필터 / 거리 필터 3종을 나눠서)
- 지속: 5분 (JIT 워밍업 이후 구간만 집계)

`typical`·`heavy` 두 볼륨에서 각각 돌린다.

### 5.3 `stress` — 무릎 찾기 (핵심 시나리오)

`ramping-arrival-rate`로 도착률을 계단식으로 올린다. 예: 20 → 40 → 60 → 80 → 120 → 160 rps, 각 단계 2분.

**이 시나리오만 임계값으로 실패시키지 않는다.** 목적이 깨뜨리는 것이기 때문이다. 대신 각 단계마다 기록한다.
- P95 / P99 응답 시간
- `http_req_failed` 비율과 **실패의 종류** (5초 커넥션 타임아웃인지, 429인지, 502인지)
- 동시에 관리 포트 지표(6절)

찾는 것은 두 개의 지점이다: **P95가 목표를 넘는 지점**과 **에러가 오르기 시작하는 지점**. 둘 사이가 좁으면(느려지자마자 곧바로 실패) 운영 여유가 없다는 뜻이고, 그게 이 테스트가 알려줄 수 있는 가장 값진 사실이다.

### 5.4 `soak` — 시간이 지나야 드러나는 것

무릎의 60% 수준 도착률로 1시간. 찾는 것은 응답 시간이 아니라 **단조 증가하는 것들**이다.
- 힙 사용량이 GC 후에도 계속 올라가는가 (누수)
- 커넥션 풀 대기(`hikaricp.connections.pending`)가 시간에 따라 쌓이는가
- 히스토리 행이 늘면서 픽 응답이 느려지는가 (2.1)

### 5.5 별도: `login` (선택)

Argon2 비용 측정용. 5 VU, 2분, `POST /api/v1/auth/login`만. 계정별 실패 제한을 피해 항상 성공하는 자격증명을 쓴다. 인증 IP 레이트 리밋(10/분) 때문에 테스트 환경에서 `RATE_LIMIT_AUTH_PER_MINUTE`를 올려야 한다 — **올렸다는 사실을 결과에 적는다.**

## 6. 동시에 봐야 할 지표

k6 숫자만으로는 "느렸다"까지만 안다. **왜** 느렸는지는 앱 안에서만 보인다. [D-027](DecisionLog.md)로 확보한 관리 포트에서 회차 내내 폴링한다.

```
docker exec menupick-app curl -s localhost:9090/actuator/metrics/<name>
```

| 지표 | 무엇을 말해주는가 |
| --- | --- |
| `hikaricp.connections.pending` | 커넥션 대기. 0보다 크면 풀(10)이 1차 병목 |
| `hikaricp.connections.active` | 10에 붙어 있으면 포화 |
| `jvm.memory.used{area=heap}` | 힙 여유. soak에서 우상향이면 누수 의심 |
| `jvm.gc.pause` | GC 정지가 P99를 만드는지 |
| `http.server.requests` | 앱이 본 지연 — k6가 본 값과의 차이가 큐잉·네트워크 몫 |
| `executor.queued{name=mailTaskExecutor}` | 로그인 시나리오에서만 의미. 메일 발송 적체 |

여유가 되면 MySQL 쪽 `SHOW GLOBAL STATUS`의 `Threads_running`, `Innodb_row_lock_waits`도 함께 본다.

## 7. 실행 환경

**k6를 대상 VM에서 돌리면 안 된다.** 앱 1536m + MySQL 1g + Redis 256m로 이미 ≈2.8GB가 물려 있는 상자에서 부하 생성기가 CPU·메모리를 같이 먹으면, 측정하려던 대상을 측정 도구가 압박한다. D-027에서 Prometheus를 미룬 것과 정확히 같은 이유다. 별도 머신에서 쏜다.

네트워크 지연이 결과에 섞이므로 러너와 대상의 위치를 기록한다. 같은 리전 안에서 쏘는 것이 기본이다.

**대상은 운영이 아니다.** 픽이 쓰기라 실제 사용자 히스토리 사이에 테스트 행이 섞이고, 4절의 시크릿 문제도 있다. 운영과 같은 구성의 별도 스택에 쏜다.

## 8. 판정 기준

| 시나리오 | 통과 조건 |
| --- | --- |
| `smoke` | 에러 0건. 픽이 200 (404면 시드 실패) |
| `load` (`typical`) | 조회 P95 < 300ms, 픽 P95 < 500ms, 실패율 < 1% |
| `load` (`heavy`) | 같은 기준. **넘으면 실패가 아니라 발견** — 인메모리 필터링의 한계선을 찾은 것이므로 백로그 #16(푸시다운)의 트리거로 기록 |
| `stress` | 임계값 없음. 무릎 지점과 1차 병목을 보고서에 남기는 것이 통과 조건 |
| `soak` | 힙·커넥션 대기가 우상향하지 않을 것. P95가 시작 대비 20% 이상 나빠지지 않을 것 |

프록시 경로(`/kakao`, `/naver`)는 P95 < 1s 목표가 있지만, **캐시 때문에 무엇을 재는지 먼저 정해야 한다.** 캐시 TTL이 1시간(카카오)·24시간(네이버)이고 좌표는 소수점 3자리로 반올림되므로, 고정 질의로 쏘면 두 번째 요청부터는 Redis만 재게 된다. 게다가 `sync=true`라 콜드 캐시에 동일 키가 몰리면 직렬화된다. 질의를 매번 바꿔 업스트림 경로를 재든지, 고정 질의로 캐시 히트 경로를 재든지 **명시적으로 고르고 결과에 적는다.**
