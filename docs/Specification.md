# 메뉴픽(MenuPick) 전체 스펙 문서

**2026-08-09** — 초기 기획서(범용 "메뉴 추천 서비스" 스펙)와 실제 구현을 대조해 현행화한 통합 스펙 문서.
상세 기술 설계(정규화·인덱스·인증·리스크)는 [Planning.md](Planning.md), 유저 스토리·KPI는 [Requirements.md](Requirements.md), 결정 근거는 [DecisionLog.md](DecisionLog.md)를 참조한다.

## 1. 프로젝트 개요

### 1.1 서비스 정의

**"오늘 뭐 먹지?" 결정 장애를 해결해주는 개인화 맛집 추천 서비스.**

사용자가 자주 먹는 메뉴와 자주 가는 식당을 직접 등록·태깅해 개인 데이터를 쌓고, 그 데이터 안에서 조건(카테고리·태그·거리)에 맞는 메뉴를 **가중치 랜덤**으로 추천받는다.

### 1.2 초기 기획 대비 방향 확정

초기 기획서는 배달 음식점 검색·레시피 검색 등 **공개 데이터 기반 검색 서비스**를 포함했으나, 실제 구현은 **사용자 본인이 쌓은 데이터 기반의 개인화 추천 서비스**로 방향을 좁혀 확정했다.

- 배달 음식점 검색(배달 예상 시간, 최소 주문 금액, 공개 리뷰): **제외** — 배달 플랫폼의 공개 API가 없어 데이터 확보가 불가능하고, 개인화 아카이빙이라는 핵심 가치와도 결이 다름. 장소 탐색 수요는 카카오 로컬/네이버 지도 API 프록시로 대체.
- 레시피 검색: **제외** — 별도 도메인(재료·조리법 데이터)이 필요한 독립 서비스 규모. 장기 확장 후보로만 유지([9.3](#93-확장-후보-장기)).

## 2. 핵심 기능

### 2.1 랜덤 메뉴 추천 — ✅ 구현 완료

`POST /api/v1/pick` 하나로 초기 기획의 랜덤 추천 4종을 모두 포괄한다.

| 초기 기획 항목 | 구현 방식 |
| --- | --- |
| 완전 랜덤 추천 | 필터 없이 픽 요청 |
| 제외 품목 설정 | 메뉴별 `is_excluded` 토글 (`PATCH /menus/{id}/exclude`) — 추천 후보에서 영구 제외 |
| 제외 카테고리 설정 | 픽 요청 시 제외 태그(`TAG_EXCLUDE`) 필터 |
| 카테고리 내 랜덤 추천 | 픽 요청 시 카테고리(`CATEGORY`) / 포함 태그(`TAG_INCLUDE`) 필터 |

초기 기획에 없던 강화 기능:

- **선호 가중치 랜덤**: 메뉴별 가중치(1~5)에 비례한 확률로 추첨. 일괄 수정 API(`PATCH /menus/weights`) 제공.
- **거리 필터**: 현재 위치 + 최대 거리(m)를 주면 반경 내 식당이 연결된 메뉴만 후보로 제한 (Haversine 계산).
- **히스토리 자동 저장**: 픽할 때마다 추천 메뉴·최근접 식당·적용 필터 조건이 자동 기록되고 응답에 `historyId` 포함.
- 후보가 없으면 `NO_PICK_CANDIDATES` 에러로 명확히 안내.

### 2.2 메뉴·맛집 아카이빙 — ✅ 구현 완료

초기 기획의 "배달 가능한 음식점 검색"을 대체하는 이 서비스의 데이터 입력 경로.

- **메뉴 관리**: CRUD + 커서 페이지네이션, 카테고리(복수), 메모, Soft delete.
- **태그 시스템**: 사용자별 자유 태그(`#혼밥`, `#국물요리` 등) 생성·삭제, 자동완성 검색(`GET /tags?keyword=`).
- **식당 저장**: 이름·주소·좌표(WGS84)·전화·네이버 장소 ID 저장, Soft delete.
- **메뉴-식당 연결**: N:M 연결에 별점(1~5)·메모 부여. 중복 연결 시 409.
- **장소 검색(외부 API 프록시)**: 카카오 로컬 키워드/카테고리 검색, 네이버 NCP 지오코딩/역지오코딩. API 키는 백엔드에만 보관하고 응답은 Redis 캐싱.

### 2.3 히스토리 & 방문 기록 — ✅ 구현 완료

- 픽 이력 최신순 커서 페이지네이션 조회 (`days` 기간 필터).
- 방문 여부 업데이트(`PATCH /history/{id}/visit`) — 실제 방문한 식당으로 덮어쓰기 가능.
- 픽 당시 적용한 필터 조건이 함께 저장되어 "그때 무슨 조건으로 뽑았는지" 회고 가능.

### 2.4 사용자 계정 — ✅ 구현 완료

- **로그인 수단 2종**: 카카오/구글 OAuth(Authorization Code 서버사이드 교환)와 이메일+비밀번호 자체 계정.
- **자체 계정**: 별도 테이블 없이 `auth_providers`의 `provider='LOCAL'` 행으로 표현한다. `UNIQUE (provider, social_id)`가 그대로 이메일 중복 가입 제약이 된다. 비밀번호는 `PasswordEncoderFactories.createDelegatingPasswordEncoder()`(현재 기본 BCrypt)로 인코딩해 `password_hash`에 저장한다 — 접두사 방식이라 이후 알고리즘 교체 시 기존 해시도 계속 검증된다.
- **메일 인증 필수**: 가입 직후에는 로그인할 수 없고, 24시간 유효한 일회용 링크를 눌러야 활성화된다. 인증 전까지 이메일은 `auth_providers.social_id`에만 있고 `users.email`은 비어 있다.
- **계정 통합**: 같은 이메일이면 기존 계정에 자동 연동한다. **검증된 이메일만** 병합 기준으로 쓴다 — `users.email`에 미검증 주소가 들어가면 공격자가 남의 주소로 먼저 가입해 피해자의 소셜 로그인을 자기 계정으로 끌어오는 탈취가 성립한다. `users.email_verified`가 이 불변식을 명시한다.
- **JWT 이중 토큰**: Access 30분(메모리) + Refresh 14일(HttpOnly 쿠키 + Redis, Rotation 정책).
- **탈퇴 30일 유예**: Soft delete → 30일 내 재로그인 시 복구, 경과 시 04:00 배치가 하드 삭제.
- **Rate Limit**: 인증 경로(소셜·자체 계정 전부) IP 기준 분당 10회 (Redis Lua, fail-open). 여기에 더해 계정 단위 로그인 실패 제한(15분 내 10회)을 둔다 — IP 버킷만으로는 여러 IP에서 한 계정을 노리는 분산 대입을 막지 못한다.

## 4. 데이터베이스 설계

정규화(1NF~5NF 검토 완료) 후 **10개 테이블**. 상세 명세·ERD·인덱스 26개 설계는 [Planning.md 3장](Planning.md#3-데이터-모델-erd-및-테이블-명세-1nf-적용) 참조.

| 테이블 | 역할 |
| --- | --- |
| `users` | 사용자 (Soft delete) |
| `auth_providers` | 소셜 연동 (1NF 분리 — provider 추가 시 스키마 변경 불필요) |
| `menus` | 메뉴 (가중치, 추천 제외 플래그, Soft delete) |
| `menu_categories` | 메뉴 카테고리 (복수 지정 가능, 1NF 분리) |
| `tags` / `menu_tags` | 사용자별 태그와 메뉴 연결 (N:M) |
| `restaurants` | 저장한 식당 (좌표 포함, Soft delete) |
| `menu_restaurants` | 메뉴-식당 연결 (별점·메모) |
| `histories` | 픽 히스토리 (방문 여부·시각) |
| `history_filter_conditions` | 픽 당시 필터 조건 (1NF 분리) |

## 5. 시스템 아키텍처와 API

### 5.1 아키텍처

레이어드 아키텍처(Controller → Service → Repository) + 외부 연동은 별도 Client 레이어. 프론트는 외부 API를 직접 호출하지 않고 백엔드 프록시를 경유한다 (API 키 비노출).

```
React SPA ── /api/v1 ──> Spring Boot ──> MySQL (Flyway)
                             ├────────> Redis (토큰·캐시·RateLimit)
                             └────────> 카카오 로컬 / 네이버 NCP Maps
```

### 5.2 API 설계 규칙 요약

- Base URL `/api/v1`, 공통 응답 포맷 `{ success, data, message, code }`, 커서 페이지네이션(size 1~100).
- 전체 엔드포인트 목록(인증 13 + 메뉴 8 + 픽 2 + 태그 3 + 식당 5 + 외부검색 4 + 메뉴-식당 4 + 히스토리 3 = **42개**)은 [Planning.md 2.5](Planning.md#25-주요-api-목록) 및 Swagger UI 참조.
- 인증 없이 열린 경로는 로그인/가입/재발급 계열 9개(소셜 2·재발급 1·자체 계정 6), 게스트 데모 픽 1개, 헬스체크뿐이다.

## 6. UI/UX 화면 설계

[Requirements.md](Requirements.md)의 US-2~US-5 기준 화면을 모두 구현했다. 로그아웃·탈퇴·세션 만료 시 react-query 캐시를 함께 비운다 — 공용 기기에서 계정을 바꿔 로그인했을 때 이전 사용자의 데이터가 남아 보이지 않도록 `AuthContext`에서 일괄 처리한다.

> **미구현**: 로그인 후 원래 가려던 경로로 돌아가는 returnUrl 복귀는 아직 없다. `ProtectedRoute`가 목적지를 남기지 않고 로그인 후 착지점은 `/menus` 고정이다. 구현 시 복원 경로가 앱 내부인지 검증해야 한다(오픈 리다이렉트 방지).

| 화면 | 구성 | 상태 |
| --- | --- | --- |
| 로그인 | 이메일+비밀번호 폼, 카카오/구글 소셜 버튼, 게스트 데모 픽 시연 + 전환 CTA. 미인증 계정으로 로그인하면 인증 메일 재발송 버튼을 준다 | ✅ 완료 |
| 가입 | 이메일·닉네임·비밀번호(확인 포함) → 인증 메일 발송 안내 화면 | ✅ 완료 |
| 메일 인증 / 비밀번호 재설정 | 메일 링크 착지점(`/verify-email`, `/reset-password`)과 재설정 요청(`/forgot-password`). 인증·재설정 성공 시 그 자리에서 로그인된다 | ✅ 완료 |
| 홈 (픽) | 필터 선택(카테고리·태그·거리) → 슬롯머신 연출 랜덤 픽 → 결과(메뉴+최근접 식당) → 다시 돌리기 | ✅ 완료 |
| 메뉴 관리 | 메뉴 목록(커서 무한스크롤)·등록·수정, 태그 자동완성 입력, 가중치/추천 제외 토글 | ✅ 완료 |
| 식당 관리 | 장소 검색(카카오) → 저장, 메뉴 연결 + 별점·메모 (지도 표시는 네이버 지도 외부 링크로 대체) | ✅ 완료 |
| 히스토리 | 픽 이력 목록(기간 필터), 방문 처리(실제 방문 식당 선택) | ✅ 완료 |
| 설정 | 계정 정보, 비밀번호 변경(자체 계정만 노출), 로그아웃, 회원 탈퇴(30일 유예 안내 + 동의 체크 2단계 확인) | ✅ 완료 |

## 7. 비기능 요구사항 (요약)

상세는 [Planning.md 7장](Planning.md#7-비기능-요구사항).

- **성능**: API P95 < 300ms, 랜덤 픽 < 500ms, 외부 프록시 < 1s. k6 부하 테스트 스크립트 보유.
- **보안**: HTTPS 강제, CORS 화이트리스트, Rate Limit, JWT Rotation, 시크릿 env 주입(JWT_SECRET fail-fast).
- **백업**: 일일 전체 백업 + Binlog PITR, 보존 14일+, RPO ≤ 24h / RTO ≤ 4h (운영 전환 시 확정).
- **관측성**: Actuator health/metrics. MDC 기반 요청 상관관계(`traceId`, 인증 시 `userId`)를 전 로그에 기록하고 `X-Request-Id` 응답 헤더로 반환 — 필터 체인 최바깥에 등록해 401·429까지 묶인다. APM은 Phase 4 예정.
- **법적**: 위치정보 활용 — 위치기반서비스사업 신고 및 처리방침 게시 필요 ([PrivacyReview.md](PrivacyReview.md)), 정식 공개 전 완료 조건.

### 9.2 Phase 7+ — 추천 고도화 제안

초기 기획의 "사용자 맞춤 추천"을 현재 데이터 모델로 실현 가능한 형태로 재정의한 확장 후보. 별도 스키마 없이 `histories` 데이터만으로 시작할 수 있다.

- **연속 중복 방지**: 최근 N일 내 픽된 메뉴의 가중치를 일시 감쇠 — "어제 먹은 거 또 나옴" 문제 해결.
- **방문율 기반 가중치 자동 보정**: 추천 후 방문 처리된 메뉴는 가중치 상향, 반복 스킵된 메뉴는 하향 제안.
- **컨텍스트 추천**: 시간대(점심/저녁)·요일·계절별 픽 패턴 반영. 초기 기획의 "계절/트렌드 반영"의 개인화 버전 — 공개 트렌드 데이터가 아니라 본인의 이력을 쓴다.
- **알레르기·기피 프리셋**: 온보딩에서 알레르기/기피 태그 프리셋을 제공하고 픽 요청의 기본 제외 태그로 저장. 초기 기획의 "알레르기 정보 설정"을 태그 시스템으로 흡수 — 프로필에 기본 필터(default filter) 저장 기능만 추가하면 됨.

### 9.3 확장 후보 (장기)

우선순위 낮음. 착수 전 기획 재검토 필요.

- **레시피 연결**: 독립 레시피 검색 대신 메뉴에 레시피 링크/메모 필드 추가, 또는 식약처 조리식품 레시피 오픈API 연동 검토.
- **AI 추천**: 히스토리·가중치 데이터가 충분히 쌓인 후 개인 모델 검토 (KPI로 룰 기반 대비 효과 검증 전제).
- **음성 검색 / 다국어(한·영)**: 초기 기획 승계 항목. 수요 확인 전 보류.
