# 메뉴픽(MenuPick) 전체 스펙 문서

**2026-08-09** — 초기 기획서(범용 "메뉴 추천 서비스" 스펙)와 실제 구현을 대조해 현행화한 통합 스펙 문서.
상세 기술 설계(정규화·인덱스·인증·리스크)는 [Planning.md](Planning.md), 유저 스토리·KPI는 [Requirements.md](Requirements.md), 결정 근거는 [DecisionLog.md](DecisionLog.md)를 참조한다.

## 1. 프로젝트 개요

### 1.1 서비스 정의

**"오늘 뭐 먹지?" 결정 장애를 해결해주는 개인화 맛집 추천 서비스.**

사용자가 자주 먹는 메뉴와 자주 가는 식당을 직접 등록·태깅해 개인 데이터를 쌓고, 그 데이터 안에서 조건(카테고리·태그·거리)에 맞는 메뉴를 **가중치 랜덤**으로 추천받는다.

### 1.2 초기 기획 대비 방향 확정

초기 기획서는 배달 음식점 검색·레시피 검색 등 **공개 데이터 기반 검색 서비스**를 포함했으나, 실제 구현은 **사용자 본인이 쌓은 데이터 기반의 개인화 추천 서비스**로 방향을 좁혀 확정했다.

- 배달 음식점 검색(배달 예상 시간, 최소 주문 금액, 공개 리뷰): **제외** — 배달 플랫폼의 공개 API가 없어 데이터 확보가 불가능하고, 개인화 아카이빙이라는 핵심 가치와도 결이 다름. 장소 탐색 수요는 카카오 로컬 API 프록시로 대체.
- 레시피 검색: **제외** — 별도 도메인(재료·조리법 데이터)이 필요한 독립 서비스 규모. 장기 확장 후보로만 유지([9.3](#93-확장-후보-장기)).

## 2. 핵심 기능

### 2.1 랜덤 메뉴 추천 — ✅ 구현 완료

`POST /api/v1/pick` 하나로 초기 기획의 랜덤 추천 4종을 모두 포괄한다.

| 초기 기획 항목 | 구현 방식 |
| --- | --- |
| 완전 랜덤 추천 | 필터 없이 픽 요청 |
| 제외 품목 설정 | 메뉴별 `is_excluded` 토글 (`PATCH /menus/{id}/exclude`) — 추천 후보에서 영구 제외 |
| 제외 카테고리 설정 | 픽 요청 시 제외 태그(`TAG_EXCLUDE`) 필터 |
| 카테고리 내 랜덤 추천 | 픽 요청 시 카테고리(`CATEGORY`) / 포함 태그(`TAG_INCLUDE`) 필터 |

초기 기획에 없던 강화 기능:

- **선호 가중치 랜덤**: 메뉴별 가중치(1~5)에 비례한 확률로 추첨. 일괄 수정 API(`PATCH /menus/weights`) 제공.
- **거리 필터**: 현재 위치 + 최대 거리(m)를 주면 반경 내 식당이 연결된 메뉴만 후보로 제한 (Haversine 계산).
- **히스토리 자동 저장**: 픽할 때마다 추천 메뉴·최근접 식당·적용 필터 조건이 자동 기록되고 응답에 `historyId` 포함.
- 후보가 없으면 `NO_PICK_CANDIDATES` 에러로 명확히 안내.

### 2.2 메뉴·맛집 아카이빙 — ✅ 구현 완료

초기 기획의 "배달 가능한 음식점 검색"을 대체하는 이 서비스의 데이터 입력 경로.

> **이 문서에서 "✅ 구현 완료"는 사용자가 화면에서 그 일을 끝까지 할 수 있다는 뜻이다.**
> API만 있고 부르는 화면이 없으면 완료가 아니다. 이 단서를 붙이는 이유는 실제로 그렇게
> 어긋난 적이 있기 때문이다 — 2026-09-03 점검에서 이 절이 "완료"인데도 (a) 메뉴에 연결한
> 식당을 **떼거나 별점·메모를 고칠 화면이 아예 없었고**, (b) 태그는 만들 수만 있고 지울 수
> 없었다. 백엔드 API와 그 테스트는 셋 다 처음부터 있었다. 지금은 화면까지 붙어 있다
> (메뉴 수정 폼의 "연결된 식당", 설정의 "태그").

- **메뉴 관리**: CRUD + 커서 페이지네이션, 카테고리(복수), 메모, Soft delete.
- **태그 시스템**: 사용자별 자유 태그(`#혼밥`, `#국물요리` 등) 생성·삭제, 자동완성 검색(`GET /tags?keyword=`). 삭제는 설정 화면에서 하고, 지우면 그 태그가 붙어 있던 모든 메뉴에서 함께 빠진다. 관리 화면이 쓰는 전체 목록은 `GET /tags?all=true`로 따로 받는다 — 자동완성은 키워드가 비면 의도적으로 빈 목록을 주기 때문이다(입력 전에 제안 칩을 펼치지 않으려고).
- **식당 저장**: 이름·주소·좌표(WGS84)·전화·카카오 장소 ID 저장, Soft delete.
- **메뉴-식당 연결**: N:M 연결에 별점(1~5)·메모 부여. 중복 연결 시 409. 연결은 식당 화면에서 만들고, 목록·수정·해제는 **메뉴 수정 폼의 "연결된 식당"** 절에서 한다. 수정은 화면을 그릴 때 받은 `version`을 그대로 실어 보내는 낙관적 락이다(D-032).
- **같은 장소 중복 저장 방지**: 이미 저장한 가게를 다시 저장하면 새로 만들지 않고 갖고 있던 식당을 200으로 돌려준다(새로 만들면 201). 판정 기준은 카카오 장소 id뿐이다 — 상호가 같은 다른 가게가 실제로 있어 이름으로 합치면 서로 다른 지점이 뭉개진다. 기존 식당은 덮어쓰지 않는다(사용자가 고쳐 둔 이름·주소를 되돌리지 않기 위해).
- **장소 검색(외부 API 프록시)**: 카카오 로컬 키워드/카테고리 검색. API 키는 백엔드에만 보관하고 응답은 Redis 캐싱. (네이버 NCP 지오코딩/역지오코딩은 **걷어냈다** — 프론트에 호출부가 0건이었다. D-035)

### 2.3 히스토리 & 방문 기록 — ✅ 구현 완료

- 픽 이력 최신순 커서 페이지네이션 조회 (`days` 기간 필터).
- 방문 여부 업데이트(`PATCH /history/{id}/visit`) — 실제 방문한 식당으로 덮어쓰기 가능.
- 개별 이력 삭제(`DELETE /history/{id}`).
- 픽 당시 적용한 필터 조건이 함께 저장되어 "그때 무슨 조건으로 뽑았는지" 회고 가능.

### 2.4 사용자 계정 — ✅ 구현 완료

- **로그인 수단 2종**: 카카오/구글 OAuth(Authorization Code 서버사이드 교환)와 이메일+비밀번호 자체 계정.
- **자체 계정**: 별도 테이블 없이 `auth_providers`의 `provider='LOCAL'` 행으로 표현한다. `UNIQUE (provider, social_id)`가 그대로 이메일 중복 가입 제약이 된다.
- **비밀번호 해싱**: **Argon2id** (`m=9216KiB, t=4, p=1`, salt 16B, hash 32B — OWASP 권장 조합 중 하나). `DelegatingPasswordEncoder`로 감싸 `{argon2}` 접두사를 붙이므로, 이후 알고리즘을 또 옮겨도 기존 해시가 계속 검증된다(bcrypt도 검증 경로에 남겨 뒀다).
  - 메모리를 OWASP의 다른 권장값(`m=19456`) 대신 낮춘 이유는 운영 컨테이너가 1536MB(힙 약 1.1GB)이고 톰캣 스레드가 50개라, 로그인이 몰리면 해싱 메모리가 그대로 힙 점유가 되기 때문이다. 19MiB면 최악의 경우 ≈950MB로 힙이 통째로 잠기지만 9MiB면 ≈450MB로 견딘다. **서버 사양을 올리면 `m`을 19456으로 올릴 것.**
  - 인코딩 결과는 접두사 포함 **104자**다. `password_hash`를 bcrypt 기준(60자)으로 잡으면 조용히 잘려 모든 로그인이 실패하므로 `VARCHAR(255)`로 둔다.
  - 검증 1회에 약 42ms가 든다(실측). 계정이 없을 때도 더미 해시로 같은 비용을 치러 응답 시간으로 가입 여부가 드러나지 않게 한다.
- **메일 인증 필수**: 가입 직후에는 로그인할 수 없고, 24시간 유효한 일회용 링크를 눌러야 활성화된다. 인증 전까지 이메일은 `auth_providers.social_id`에만 있고 `users.email`은 비어 있다.
- **메일 발송 격리**: SMTP 발송은 전용 스레드 풀(코어 2·최대 4·큐 100)에서 비동기로 일어나므로 가입·재설정 응답이 SMTP 왕복을 기다리지 않는다. 큐가 차면 `CallerRunsPolicy`가 호출 스레드에서 그대로 발송한다 — 인증 메일을 조용히 버리느니 느려지는 편을 택한 것이다. 발송 실패는 예외로 올라오지 않고(풀 스레드에서 던져봐야 호출자에게 닿지 않는다) 로그로만 남으며, 사용자 쪽 복구는 재발송·재요청 경로가 담당한다.
- **메일 발송 타임아웃**: Jakarta Mail의 연결·응답·쓰기 타임아웃 기본값은 셋 다 무한이다. 그대로 두면 응답 없는 SMTP 서버가 발송 풀 4개를 영구히 잠가 신규 가입이 통째로 막히고, 큐까지 차면 `CallerRunsPolicy`를 타고 톰캣 스레드(50개)로 번진다. 연결 5초(WebClient와 동일)·응답/쓰기 10초를 건다. 외부 JSON 호출(카카오 3초)보다 넉넉한 이유는 SMTP가 왕복이 여러 번인 대화형 프로토콜이기 때문이다.
- **닉네임 중복 불가**: 자체 가입은 중복이면 409로 거절한다. 소셜 로그인은 거절하지 않고 번호를 붙인다(`홍길동` → `홍길동2`) — 닉네임은 제공자가 주는 값이라 사용자가 고른 적이 없고, 흔한 이름이라는 이유로 막으면 로그인 자체가 불가능해진다([D-028](DecisionLog.md#d-028-유일성-규칙--닉네임은-중복-불가-식당은-카카오-place-id-기준으로-하나)).
- **계정 통합**: 같은 이메일이면 기존 계정에 자동 연동한다. **검증된 이메일만** 병합 기준으로 쓴다 — `users.email`에 미검증 주소가 들어가면 공격자가 남의 주소로 먼저 가입해 피해자의 소셜 로그인을 자기 계정으로 끌어오는 탈취가 성립한다. `users.email_verified`가 이 불변식을 명시한다.
- **JWT 이중 토큰**: Access 30분(메모리) + Refresh 14일(HttpOnly 쿠키 + Redis, Rotation 정책).
- **탈퇴 30일 유예**: Soft delete → 30일 내 재로그인 시 복구, 경과 시 04:00 배치가 하드 삭제.
- **Rate Limit**: 인증 경로(소셜·자체 계정 전부) IP 기준 분당 10회 (Redis Lua, fail-open). 여기에 더해 계정 단위 로그인 실패 제한(15분 내 10회)을 둔다 — IP 버킷만으로는 여러 IP에서 한 계정을 노리는 분산 대입을 막지 못한다.

## 4. 데이터베이스 설계

정규화(1NF~5NF 검토 완료) 후 **10개 테이블**. 상세 명세·ERD·인덱스 26개 설계는 [Planning.md 3장](Planning.md#3-데이터-모델-erd-및-테이블-명세-1nf-적용) 참조.

| 테이블 | 역할 |
| --- | --- |
| `users` | 사용자 (Soft delete). `email`·`nickname` 각각 UNIQUE |
| `auth_providers` | 소셜 연동 (1NF 분리 — provider 추가 시 스키마 변경 불필요) |
| `menus` | 메뉴 (가중치, 추천 제외 플래그, Soft delete) |
| `menu_categories` | 메뉴 카테고리 (복수 지정 가능, 1NF 분리) |
| `tags` / `menu_tags` | 사용자별 태그와 메뉴 연결 (N:M) |
| `restaurants` | 저장한 식당 (좌표 포함, Soft delete). `(user_id, kakao_place_id)` UNIQUE — 같은 장소를 두 번 저장하지 않는다 |
| `menu_restaurants` | 메뉴-식당 연결 (별점·메모) |
| `histories` | 픽 히스토리 (방문 여부·시각) |
| `history_filter_conditions` | 픽 당시 필터 조건 (1NF 분리) |

## 5. 시스템 아키텍처와 API

### 5.1 아키텍처

레이어드 아키텍처(Controller → Service → Repository) + 외부 연동은 별도 Client 레이어. 프론트는 외부 API를 직접 호출하지 않고 백엔드 프록시를 경유한다 (API 키 비노출).

```
React SPA ── /api/v1 ──> Spring Boot ──> MySQL (Flyway)
                             ├────────> Redis (토큰·캐시·RateLimit)
                             └────────> 카카오 로컬
```

### 5.2 API 설계 규칙 요약

- Base URL `/api/v1`, 공통 응답 포맷 `{ success, data, message, code }`, 커서 페이지네이션(size 1~100).
- 전체 엔드포인트 목록(인증 17 + 메뉴 8 + 식당 5 + 메뉴-식당 4 + 태그 3 + 히스토리 3 + 픽 2 + 외부검색 2 = **44개**)은 [Planning.md 2.5](Planning.md#25-주요-api-목록) 및 Swagger UI 참조. (2026-09-03에 실제 컨트롤러 기준으로 다시 셌다 — 인증은 자체 계정 경로가 늘어 13→17, 외부검색은 네이버를 걷어내 4→2다.)
- 인증 없이 열린 경로는 로그인/가입/재발급 계열 9개(소셜 2·재발급 1·자체 계정 6), 게스트 데모 픽 1개, 헬스체크뿐이다.

## 6. UI/UX 화면 설계

[Requirements.md](Requirements.md)의 US-2~US-5 기준 화면을 모두 구현했다. 로그아웃·탈퇴·세션 만료 시 react-query 캐시를 함께 비운다 — 공용 기기에서 계정을 바꿔 로그인했을 때 이전 사용자의 데이터가 남아 보이지 않도록 `AuthContext`에서 일괄 처리한다.

**로그인 후 복귀(returnUrl)**: `ProtectedRoute`가 막힌 경로를 sessionStorage(`returnTo`)에 남기고, 이메일·소셜 로그인이 모두 그 자리로 되돌린다(`auth/returnTo.ts`). 라우터 state 대신 sessionStorage를 쓰는 이유는 소셜 로그인이 문서를 통째로 갈아끼우는 전체 리다이렉트라 메모리 값이 왕복 중에 사라지기 때문이다 — 두 경로가 서로 다른 수단을 쓰면 로그인 방식에 따라 도착지가 달라진다. 꺼낼 때 값이 앱 내부 경로인지 검증한다: sessionStorage는 같은 오리진의 어떤 스크립트든 쓸 수 있어, `//evil.com`이나 `/\evil.com`처럼 경로로 위장한 값을 그대로 따라가면 **로그인 직후라 신뢰도가 가장 높은 순간에** 외부 사이트로 나가는 오픈 리다이렉트가 된다. 기억해 둔 값이 없으면 `/menus`로 간다.

**접근성**: 앱 안쪽 화면의 제목은 `h1`이고 그 아래 폼 제목이 `h2`다(크기는 `.page h1`로 맞춘다) — 제목만 훑는 스크린리더 사용자가 지금 어느 화면인지 알 수 있어야 한다. 선택 상태를 색으로만 보여주던 칩·기간 버튼에는 `aria-pressed`를 붙였다(`a11y/chipToggle.ts`가 클래스와 함께 만들어 어긋남을 막는다). 메뉴·식당의 수정 폼은 카드를 통째로 대체해 눌렀던 버튼이 사라지므로, 열 때 폼 제목으로 초점을 옮기고(`a11y/useFocusOnMount.ts`) 닫을 때 다시 그려진 버튼으로 되돌린다.

| 화면 | 구성 | 상태 |
| --- | --- | --- |
| 로그인 | 이메일+비밀번호 폼, 카카오/구글 소셜 버튼, 게스트 데모 픽 시연 + 전환 CTA. 미인증 계정으로 로그인하면 인증 메일 재발송 버튼을 준다 | ✅ 완료 |
| 가입 | 이메일·닉네임·비밀번호(확인 포함) → 인증 메일 발송 안내 화면 | ✅ 완료 |
| 메일 인증 / 비밀번호 재설정 | 메일 링크 착지점(`/verify-email`, `/reset-password`)과 재설정 요청(`/forgot-password`). 인증·재설정 성공 시 그 자리에서 로그인된다 | ✅ 완료 |
| 홈 (픽) | 필터 선택(카테고리·태그·거리) → 슬롯머신 연출 랜덤 픽 → 결과(메뉴+최근접 식당) → 다시 돌리기 | ✅ 완료 |
| 메뉴 관리 | 메뉴 목록(커서 무한스크롤)·등록·수정, 태그 자동완성 입력, 가중치/추천 제외 토글, **연결된 식당** 목록·별점/메모 수정·연결 해제 | ✅ 완료 |
| 식당 관리 | 장소 검색(카카오) → 저장, 메뉴에 연결 + 별점·메모 (지도 표시는 저장된 지도 링크를 외부로 여는 것으로 대체). 연결을 **고치거나 떼는 것은 메뉴 관리 화면**에서 한다 | ✅ 완료 |
| 히스토리 | 픽 이력 목록(기간 필터), 방문 처리(실제 방문 식당 선택) | ✅ 완료 |
| 설정 | 계정 정보, 소셜 연동/해제, 비밀번호 변경(자체 계정만 노출), **태그 삭제**, 로그아웃, 회원 탈퇴(30일 유예 안내 + 동의 체크 2단계 확인) | ✅ 완료 |

## 7. 비기능 요구사항 (요약)

상세는 [Planning.md 7장](Planning.md#7-비기능-요구사항).

- **성능**: API P95 < 300ms, 랜덤 픽 < 500ms, 외부 프록시 < 1s. k6 부하 테스트 스크립트 보유.
- **보안**: HTTPS 강제, CORS 화이트리스트, Rate Limit, JWT Rotation, 시크릿 env 주입(JWT_SECRET fail-fast).
- **백업**: 일일 전체 백업 + Binlog PITR, 보존 14일+, RPO ≤ 24h / RTO ≤ 4h (운영 전환 시 확정).
- **관측성**: Actuator health/metrics. MDC 기반 요청 상관관계(`traceId`, 인증 시 `userId`)를 전 로그에 기록하고 `X-Request-Id` 응답 헤더로 반환 — 필터 체인 최바깥에 등록해 401·429까지 묶인다. APM은 Phase 4 예정.
- **법적**: 위치정보 활용 — 위치기반서비스사업 신고 및 처리방침 게시 필요 ([PrivacyReview.md](PrivacyReview.md)), 정식 공개 전 완료 조건.

## 8. 추천 품질 KPI

[Requirements.md 2장](Requirements.md#2-추천-품질-지표-kpi) 기준, 현재 스키마로 바로 계산 가능한 3개 지표를 추적한다.

| 지표 | 정의 | 초기 목표 |
| --- | --- | --- |
| 픽 후 방문율 | 추천받은 메뉴를 실제 방문 처리한 비율 | ≥ 30% |
| 재픽률 | 같은 날 픽을 다시 요청한 사용자 비율 (낮을수록 좋음) | ≤ 20% |
| 7일 리텐션 | 첫 픽 후 7일 내 재픽 사용자 비율 | ≥ 25% |

> **집계 수단은 아직 없다 (⬜).** 세 지표 모두 "현재 스키마로 바로 계산 가능"한 것은 맞지만,
> 실제로 계산하는 코드도 이 값을 볼 수 있는 화면·대시보드도 없다. 목표치(30%/20%/25%)만
> 적혀 있고 현재값을 아무도 모르는 상태다. 공개 시점에 맞춰 집계 수단을 붙이거나, 붙이지
> 않기로 한다면 이 표를 지우고 "추적하지 않는다"고 적는 편이 낫다 — 목표만 남은 지표는
> 달성 여부를 물었을 때 답할 수 없다.

### 9.2 Phase 7+ — 추천 고도화 제안

초기 기획의 "사용자 맞춤 추천"을 현재 데이터 모델로 실현 가능한 형태로 재정의한 확장 후보. 별도 스키마 없이 `histories` 데이터만으로 시작할 수 있다.

- **연속 중복 방지**: 최근 N일 내 픽된 메뉴의 가중치를 일시 감쇠 — "어제 먹은 거 또 나옴" 문제 해결.
- **방문율 기반 가중치 자동 보정**: 추천 후 방문 처리된 메뉴는 가중치 상향, 반복 스킵된 메뉴는 하향 제안.
- **컨텍스트 추천**: 시간대(점심/저녁)·요일·계절별 픽 패턴 반영. 초기 기획의 "계절/트렌드 반영"의 개인화 버전 — 공개 트렌드 데이터가 아니라 본인의 이력을 쓴다.
- **알레르기·기피 프리셋**: 온보딩에서 알레르기/기피 태그 프리셋을 제공하고 픽 요청의 기본 제외 태그로 저장. 초기 기획의 "알레르기 정보 설정"을 태그 시스템으로 흡수 — 프로필에 기본 필터(default filter) 저장 기능만 추가하면 됨.

### 9.3 확장 후보 (장기)

우선순위 낮음. 착수 전 기획 재검토 필요.

- **레시피 연결**: 독립 레시피 검색 대신 메뉴에 레시피 링크/메모 필드 추가, 또는 식약처 조리식품 레시피 오픈API 연동 검토.
- **AI 추천**: 히스토리·가중치 데이터가 충분히 쌓인 후 개인 모델 검토 (KPI로 룰 기반 대비 효과 검증 전제).
- **음성 검색 / 다국어(한·영)**: 초기 기획 승계 항목. 수요 확인 전 보류.
