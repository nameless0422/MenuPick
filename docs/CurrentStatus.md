## 제품 완성도

### 2026-10-05 방문 기록의 메뉴 ID로 식당 선택

- 이력 API의 각 항목에 활성 메뉴 `menuId`를 추가하고, 그 ID로 연결 식당을 조회한다.
  메뉴 이름을 첫 100개 목록과 대조하던 방식을 없애 같은 이름의 메뉴와 오래된 메뉴도
  식당을 선택할 수 있다. 화면 진입 시 준비용 메뉴 목록 API 1회도 제거했다.
- 삭제된 메뉴는 이름을 기록에 남기되 `menuId=null`로 응답한다. 참조 없는 메뉴와 구버전
  서버가 ID를 생략한 경우는 식당을 추측하지 않고 기본 방문 처리를 제공한다. 식당 조회는
  버튼을 눌렀을 때만 실행하며, 실패하면 방문을 기록하지 않고 재시도할 수 있다.
- DB 마이그레이션과 추가 조회는 없다. 로컬 백엔드 `check` 883개, 프런트 lint·build·Vitest
  488개, Playwright 6개가 통과했다. 실제 MySQL에서 ID 직렬화와 삭제 후 이름 보존을 확인했고,
  같은 이름의 메뉴, 다음 페이지, null·필드 부재와 식당 조회 재시도를 검증했다.
  PR #329와 `main`의 frontend·test·docker-build CI도 모두 통과했다.
- `main` SHA `69d4ae286dfca401bc1608b1cd387d402f9ab6e8`로 운영 배포했다. 배포 전 백업
  `menupick-20261004-164158Z.sql.gz`의 압축 무결성과 덤프 완료 표지를 확인했다. 배포 후 다섯
  컨테이너 healthy, readiness·전체 health UP, HTTPS 200, HTTP 301, 미인증 이력 API 401,
  새 웹 번들의 메뉴 ID 사용과 기존 메뉴 목록 조회 코드 제거, app/web ARM64 이미지,

### 2026-10-04 메뉴 잠시 쉬기 — 운영 배포 완료

- 메뉴를 기간을 정해(3일·1주·2주·1달, 서버는 1~90일) 추천에서 쉬게 하고, 언제든 바로 깨울 수 있다.
  쉬는 메뉴는 픽·픽 대안·같이 뽑기 방 후보에서 모두 빠지고, 메뉴 목록에는 "쉬는 중 · N일 남음"

  수행할 스케줄러도 없다. 기간이 지나도 값을 지우지 않으므로 화면은 null이 아니라 지금과
  비교해서 판단한다(`frontend/src/routes/menuPause.ts`).
- DB 마이그레이션 V18(`ALGORITHM=INPLACE, LOCK=NONE`). 로컬 `./gradlew check`, 프런트

### 2026-10-04 unhealthy 자동 복구 — 운영 적용 완료

- `Up (unhealthy)`로 머무는 컨테이너를 2분마다 보고 되살린다. `restart: unless-stopped`는
  프로세스가 끝났을 때만 반응하므로 지금까지는 헬스체크가 빨간불인데 아무도 조치하지 않았다.
- 규칙: **꺼진 컨테이너는 건드리지 않는다**(검증 후 내려 두는 운영 방식), 연속 2회 관찰 뒤에
  조치(최대 4분), 같은 컨테이너는 10분 쿨다운, 3회 실패하면 멈추고 사람을 부른다. 조치·포기·복구를
  모두 웹훅으로 알린다. 재시작은 `docker restart`라 컨테이너가 바뀌지 않아 로그가 끊기지 않는다.
- 서버에서 일부러 unhealthy 컨테이너를 만들어 전 경로를 확인했다: 1회 관찰은 지켜보고 2회에
  재시작, 누적 3회 뒤 포기 알림 1건과 그 뒤 침묵, 헬스체크 실패 출력이 알림에 실리는 것,
  고친 뒤 `🟢 복구됨` 알림과 카운터 삭제, 정지된 컨테이너를 건너뛰는 것까지 봤다.
- **검증 중 버그 하나를 잡았다.** 재시작 직후에는 반드시 `starting`을 거치는데, 그 상태를
  "복구"로 보고 누적 카운터까지 지우고 있었다 — 그대로 두면 3회 제한과 쿨다운이 영구히 리셋되어
  재시작으로 고쳐지지 않는 고장에서 영원히 4분마다 재시작만 반복하고 사람을 부르지 않는다.
  `starting`에서는 연속 관찰만 끊고 누적은 보존하도록 고쳤다(PR #323의 두 번째 커밋).
- 디스크도 함께 정리했다: 미사용 배포 이미지 72개(7.94GB), dnf 캐시(약 1GB), 서버에 남아 있던
  `~/.gradle`·`~/verify`·배포 tar(515MB). 루트 77% → 50%(30G 중 15G 사용). 재발 방지로 배포 절차에
  `docker image prune -a -f` 단계를 넣었다(PR #321). 익명 MySQL 볼륨 2개(424MB, 2026-08-21
  재구축기 흔적)는 요청에 따라 남겨 두었다.
- **남은 사용자 작업**: 웹훅 URL(`/etc/menupick/alert.env`). 넣기 전까지는 알림이 journal
  경고로만 남는다.
- 여전히 없는 것: 외부 가용성 감시(컨테이너를 내려 두는 운영 방식과 충돌해 설계가 필요하다),
  지표 시계열, 디스크 임계값 알림, 장애 런북.
- 컨테이너는 계속 정지 상태이며 이 작업으로 올리지 않았다.

### 2026-10-03 실패 알림·로그 보존 — 운영 적용 완료

- 유닛 실패(`OnFailure=`)와 앱 ERROR 로그(15분 타이머)를 웹훅으로 알리는 경로를 만들었다.
  자격증명처럼 생긴 값은 마스킹하고, 웹훅 URL은 `/etc/menupick/alert.env`(0600 root)에만 두며
  journal에도 출력하지 않는다. 같은 ERROR는 1시간에 한 번만 보낸다. 컨테이너가 꺼져 있으면
  조용하지만, 그 상태에서 매일 실패하던 백업은 이제 알림으로 온다.
- 운영 컨테이너 로그를 json-file → journald로 모두 전환했다(mailpit 포함. web은 2026-09-11에
  이미 journald였다). 삭제된 컨테이너(`90cefb91ef89`)의 로그 86줄이 재생성 뒤에도 조회되는 것과
  `docker logs`가 그대로 동작하는 것을 확인했다.
- **영구 journal이 설정만 돼 있고 실제로는 꺼져 있었다.** `Storage=persistent`인데 450MB
  전부가 tmpfs(`/run/log/journal`)에 있고 `/var/log/journal`은 0바이트였다 — 마지막 부팅(9-01)의
  `systemd-journal-flush`가 디렉터리 생성(9-11) 전에 끝났고 그 뒤 재부팅이 없었다. 재부팅 한 번에
  전부 사라질 상태였다. `journalctl --flush`로 197MB를 영구 저장소로 옮기고 마커를 확인했다.
  옛 드롭인(`persistent.conf`, 상한 200M)이 알파벳 순서상 뒤여서 새 상한 1G를 덮어쓰고 있던 것도
  함께 정리했다.
- 검증: 점검 발송(`--test`), 실제 백업 실패 알림(원인 줄 `menupick-mysql 가 healthy가 아니다`까지
  포함), ERROR 감시의 조용한 경로(0건)와 알림 경로(1건, `PASSWORD=***` 마스킹), 쿨다운 동작,
  URL이 비었을 때 경고 한 줄로 정상 종료(exit 0)를 모두 서버에서 확인했다. 검증에는 로컬
  수신기(127.0.0.1)를 썼고 끝난 뒤 지웠다.
- **남은 사용자 작업**: 디스코드/슬랙 웹훅 URL 발급 후 `/etc/menupick/alert.env`의
  `ALERT_WEBHOOK_URL=`에 넣고 `sudo /usr/local/bin/menupick-alert --test`로 확인. 그때까지는
  알림이 journal 경고로만 남는다.
- 여전히 없는 것: 외부 가용성 감시, unhealthy 자동 재시작, 지표 시계열, 디스크 임계값 알림.
  루트 디스크는 77%(30G 중 23G)다.

- 필터 픽 12건 중 `history_filter_conditions` INSERT 3건이 한 번으로 묶이지 않는데, 배치
  설정 문제가 아니라 **IDENTITY 키 생성** 때문이다(생성된 키를 받으려 즉시 실행해야 해
  JDBC 배치가 성립하지 않는다). 줄이려면 키 전략을 바꿔야 하고 그건 마이그레이션이라
  여기서 다루지 않았다.

### 2026-09-13 상황별 빠른 픽 (프리셋)

자주 쓰는 픽 조건에 이름을 붙여 저장하고 다시 실행한다(사용자당 10개). 설계는
[PickPresetDesign.md](PickPresetDesign.md), 결정 근거는 [D-039](DecisionLog.md)·[D-040](DecisionLog.md).

- 저장하는 것은 카테고리·포함 태그·**추가** 제외 태그·거리뿐이다.
- **좌표를 저장하지 않는다.** 거리 기준점은 실행할 때마다 브라우저에서 새로 받는다 —
  회사에서 만든 프리셋을 집에서 눌렀을 때 회사 주변을 뽑지 않기 위해서다.
- **기본 제외 태그를 복사하지 않고** 실행할 때마다 최신 값을 합친다. 프리셋이 기본 제외를
  **해제할 수단은 없다**. 유효 제외가 50개를 넘으면 자르지 않고 409로 멈춘다.
- **참조 태그가 지워지면 실행이 막힌다**(`needsReview`, 버전도 함께 오른다). 사용자가 전체
  조건을 다시 확인해 저장해야 풀린다 — 조건이 조용히 넓어진 채로 추천이 나가지 않게.
- 실행은 전용 경로 `POST /pick/presets/{id}/pick`이고 필터 override를 받지 않는다.
  일반 `POST /pick`의 계약(명시 제외 20 상한, null/빈 배열 의미)과 **쿼리 예산 7/12는 그대로다.**
  빠른 픽 실행은 별도 예산 14로 따로 고정했다.
- `main` 커밋 `c4e0bd7`로 **운영 배포를 완료했다**(2026-09-13).
