# 설계·구현 결정 기록 (Decision Log)

이 문서는 "왜 이렇게 만들었는가"를 모아두는 곳이다. Planning.md가 "무엇을 어떻게 만들 것인가"(설계 명세)라면, 이 문서는 그 설계·구현 과정에서 **검토한 대안과 트레이드오프, 그래서 이걸 선택한 이유**를 기록한다. 코드만 봐서는 복원할 수 없는 맥락(왜 이 방식을 버렸는지, 어떤 대안을 저울질했는지)이 핵심이다.

## 사용법

- **프로젝트 진행하면서 계속 갱신한다.** 설계 방향을 바꾸거나, "이렇게 할 수도 있었는데 이 이유로 안 했다"는 논의가 나오면 아래 템플릿으로 항목을 추가한다.
- 이미 Planning.md 등 다른 문서에 트레이드오프가 충분히 적혀 있으면 여기서는 요약 + 링크만 남긴다. 내용을 두 곳에 완전히 복제하지 않는다.
- 상태가 바뀌면(예: "보류"였던 게 실제로 구현됨) 기존 항목을 고쳐 쓴다. 새 항목을 또 만들지 않는다.
- ID는 `D-순번`으로 계속 이어 붙인다. 지운 항목의 번호는 재사용하지 않는다(히스토리 추적용).

- **트레이드오프**: 무엇을 포기했는가, 어떤 조건이 바뀌면 재검토해야 하는가
- **관련**: 코드 위치 / 다른 문서 링크

## A. 인증·보안

### D-001. 계정 통합 정책 — 이메일 기준 자동 통합

- **날짜**: 2026-07-06
- **상태**: 채택
- **배경**: `auth_providers`는 유저 1명에 소셜 N개 연동을 전제로 설계했지만, 로그인 로직은 provider별로 새 유저를 만들어 같은 사람이 카카오/구글로 각각 로그인하면 계정이 2개로 쪼개졌다. 게다가 `users.email` UNIQUE 제약 때문에 두 번째 소셜 로그인은 500 에러로 죽었다.
- **검토한 대안**:
  1. **이메일 기준 자동 통합** — 가입 전 이메일로 기존 유저를 찾아 있으면 auth_provider 행만 추가. 사용자 개입 없이 바로 통합됨 / 이메일을 사실상 식별자로 취급하게 되어, 이메일이 없거나(널) 위조 가능한 provider가 섞이면 위험.
  2. 마이페이지에서 수동 연동 — 사용자가 명시적으로 동의하고 연동. 더 안전하지만 UX 마찰 크고 초기 개인 프로젝트 규모에 과함.
  3. 통합하지 않음(계정=소셜 단위) — 구현 단순하지만 "같은 사람인데 메뉴/히스토리가 갈린다"는 문제가 남음.
- **결정**: ①. `AuthService.createNewUser`가 가입 전 이메일로 기존 유저를 조회, 있으면 새 유저를 만들지 않고 기존 유저에 `AuthProvider`만 추가한다.
- **트레이드오프**: 카카오가 이메일을 안 주거나(널) 이메일 인증이 느슨한 provider가 추가되면 계정 탈취 벡터가 될 수 있다. 현재는 카카오/구글만 써서 위험이 낮다고 판단했다 — provider를 늘릴 때 재검토 필요.
- **관련**: `AuthService.java` (`createNewUser`, `findUserByEmail`), [Planning.md 4.1](Planning.md#41-소셜-로그인-플로우)

### D-002. Refresh Token 전달 방식 — HttpOnly Cookie

- **날짜**: 2026-07-06
- **상태**: 채택
- **배경**: 클라이언트가 웹 기반으로 확정되기 전까지는 JSON 바디로 Refresh Token을 내려주고 있었는데, 이는 XSS에 취약하고 Planning.md의 애초 설계("HttpOnly Cookie 권장")와도 모순이었다.
- **검토한 대안**:
  1. **HttpOnly Cookie** — JS로 접근 불가해 XSS로 탈취 불가 / CSRF 방어를 다시 설계해야 하고, 모바일 앱 클라이언트와는 궁합이 나쁨.
  2. JSON 바디(기존) — 클라이언트 유형 무관, 구현 단순 / 저장 위치(localStorage 등) 선택이 클라이언트 책임이 되고 XSS에 노출.
- **결정**: ①. 클라이언트가 웹 전용으로 확정되어 모바일 궁합 문제가 사라졌으므로 보안이 더 강한 쿠키 방식 채택. `HttpOnly + Secure + SameSite=Strict + Path=/api/v1/auth`.
- **트레이드오프**: CSRF는 disable 상태를 유지하되, `SameSite=Strict`가 교차 사이트 전송 자체를 막아준다는 논리로 대체했다(→ D-006). 프론트와 API가 **동일 사이트**로 배포되어야 하는 제약이 생겼다 — 나중에 앱 클라이언트를 추가하면 이 결정 전체를 재검토해야 한다.
- **관련**: `AuthController.java`, `AuthCookieProperties.java`, [Planning.md 4.2](Planning.md#42-jwt-토큰-정책)

### D-003. Access/Refresh 토큰 구분 — `token_type` 클레임

- **날짜**: 2026-06 (코드 분석 기반 이슈 수정)
- **상태**: 채택
- **배경**: 초기 구현은 Access Token과 Refresh Token을 같은 방식으로 서명해서, Refresh Token을 Authorization 헤더에 넣으면 그대로 API 인증에 통과했다. 만료 주기가 긴 Refresh Token이 사실상 장기 Access Token처럼 악용될 수 있는 구멍이었다.
- **검토한 대안**:
  1. **JWT 클레임에 `token_type`("access"/"refresh") 추가, 용도별 검증 메서드 분리** — 기존 토큰 발급 구조를 크게 안 바꾸고 검증 단계에서 막을 수 있음.
  2. 서로 다른 시크릿으로 서명 — 완전히 분리되지만 키 관리가 두 배로 늘고 기존 인프라(단일 `JWT_SECRET`) 변경 필요.
- **결정**: ①. `JwtTokenProvider`가 토큰 생성 시 `token_type` 클레임을 넣고, `JwtAuthenticationFilter`는 `validateAccessToken`만, `/auth/refresh`는 `validateRefreshToken`만 통과시킨다.
- **트레이드오프**: 클레임 위조는 서명 검증으로 막히므로 안전하지만, 이 필드가 없는(구버전) 토큰은 자동으로 무효 처리된다 — 배포 시 기존 발급 토큰 전체가 무효화되는 게 맞는 전제였다(서비스 초기라 사용자 영향 없음).
- **관련**: `JwtTokenProvider.java:28-62`, `JwtAuthenticationFilter.java`

### D-004. 탈퇴 유저 재가입 — 재활성화 방식 (하드 삭제 대신 유예기간)

- **날짜**: 2026-06 (코드 분석 기반 이슈 수정), 2026-07-06 P1 보완
- **상태**: 채택
- **배경**: 처음에는 탈퇴 유저가 재로그인하면 막혀 있었다(재가입 불가) — GDPR류 "잊혀질 권리"와 사용자 편의 사이에서 방향이 없었다.
- **검토한 대안**:
  1. **Soft delete + 30일 유예기간 재활성화, 유예 경과 후 하드 삭제** — 실수 탈퇴 복구 가능, 데이터 보존 기간이 명확해 개인정보 보관 원칙에도 맞음.
  2. 탈퇴 즉시 하드 삭제 — 구현 단순, "잊혀질 권리" 관점에서 깔끔 / 실수 탈퇴 시 복구 수단이 전혀 없음.
  3. 탈퇴 후 영구 보존(소프트 삭제만, 하드 삭제 없음) — 복구는 쉽지만 개인정보를 무기한 들고 있게 되어 법적 리스크.
- **결정**: ①. `User.softDelete/reactivate`, 매일 04:00 배치(`WithdrawnUserCleanupScheduler`)로 유예기간 경과 유저를 하드 삭제. 재로그인 시 이메일/닉네임을 최신 OAuth 프로필로 갱신한다(오래된 정보로 복구되는 것 방지).
- **트레이드오프**: 하드삭제 배치는 단일 인스턴스 전제다(→ D-016). 유예기간(30일)이 지나면 정말로 복구 불가능 — 사용자에게 이 사실을 명확히 고지해야 한다([PrivacyReview.md](PrivacyReview.md)).
- **관련**: `User.java`, `AuthService.java:47`, `WithdrawnUserCleanupScheduler.java`, [Planning.md 4.4](Planning.md#44-회원-탈퇴-및-재가입-정책)

### D-005. Rate Limit — Redis Lua 원자적 처리 + Fail-open

- **날짜**: 2026-06 (코드 분석 기반 이슈 수정)
- **상태**: 채택
- **배경**: 초기 구현은 `INCR`과 `EXPIRE`를 별도 명령으로 호출했는데, 그 사이 프로세스가 죽으면 TTL 없는 카운터 키가 영구히 남아 해당 IP가 계속 차단되는 버그가 있었다. 또한 Redis 자체가 죽으면 로그인 API 전체가 막혀야 하는지도 불명확했다.
- **검토한 대안**:
  1. **Lua 스크립트로 INCR+EXPIRE 원자화, Redis 예외 시 fail-open(요청 통과 + 경고 로그)** — 카운터 누수 방지 + 인프라 장애가 핵심 기능(로그인) 장애로 안 번짐 / 짧은 시간 동안은 rate limit이 무력화될 수 있음(허용된 리스크).
  2. Fail-closed(Redis 장애 시 전체 차단) — 안전하지만 캐시 인프라 장애가 곧 서비스 전체 장애가 되는 게 더 나쁘다고 판단.
- **결정**: ①. `RateLimitFilter`에서 Lua 스크립트 사용, `catch (Exception e)`로 감싸 Redis 장애 시 통과.
- **트레이드오프**: Redis가 죽어 있는 동안은 브루트포스 방어가 사실상 없다 — Redis 자체의 가용성 리스크와 별개로 감수하기로 한 결정(→ D-015와 연결).
- **관련**: `RateLimitFilter.java:35-65`

### D-006. CSRF 비활성 유지 — SameSite=Strict로 방어

- **날짜**: 2026-07-06 (D-002와 함께 결정)
- **상태**: 채택
- **배경**: D-002로 Refresh Token이 쿠키를 타게 되면서, "쿠키 인증 = CSRF 취약"이라는 일반론이 이 프로젝트에도 그대로 적용되는지 재검토가 필요했다.
- **검토한 대안**:
  1. **CSRF 계속 disable, `SameSite=Strict`로 방어** — 쿠키로 인증되는 엔드포인트가 `/auth/refresh` 하나뿐이고, 그마저도 Strict 쿠키라 교차 사이트 요청에는 애초에 브라우저가 쿠키를 실어 보내지 않는다. 나머지 API는 Authorization 헤더 기반이라 CSRF 공격 자체가 성립 안 함.
  2. CSRF 토큰 재도입 — 표준적이지만, 이 프로젝트는 세션이 아닌 stateless JWT + REST API라 CSRF 토큰 발급/검증 배관을 새로 깔아야 해 얻는 것 대비 복잡도가 큼.
- **결정**: ①.
- **트레이드오프**: `SameSite=Strict`는 구형 브라우저(Safari 구버전 등) 호환성이 100%는 아니다. 또한 이 논리는 "프론트·API가 동일 사이트"라는 D-002의 전제가 깨지면 함께 무너진다 — 서브도메인이 아닌 완전히 다른 도메인으로 배포하게 되면 재검토 필요.
- **관련**: `SecurityConfig.java:48`, [Planning.md 4.2](Planning.md#42-jwt-토큰-정책)

### D-007. `AuthCookieProperties`를 `JwtProperties`와 분리

- **날짜**: 2026-07-06
- **상태**: 채택
- **배경**: 쿠키의 `secure` 속성을 어디에 둘지 — 의미상으로는 JWT/인증과 가까워 `JwtProperties`에 넣고 싶었다.
- **검토한 대안**:
  1. `JwtProperties`에 `cookieSecure` 필드 추가 — 관련 설정을 한 곳에 모을 수 있음 / `JwtTokenProviderTest` 3곳, `AuthServiceTest` 1곳의 `new JwtProperties(secret, ...)` 생성자 호출이 전부 깨짐.
  2. **별도 `AuthCookieProperties` record 신설** — 기존 테스트 무변경 / 설정이 두 클래스로 나뉘어 응집도는 약간 떨어짐.
- **결정**: ②. `RateLimitProperties`와 같은 패턴(`@ConfigurationProperties` + `@DefaultValue`)으로 만들어 `SecurityConfig`에 등록.
- **트레이드오프**: 인증 관련 설정이 `JwtProperties`/`AuthCookieProperties` 두 곳에 분산됐다. 설정 클래스가 더 늘어나면 인증 설정을 모아 보여주는 문서(Planning.md 6장)가 유일한 전체 그림이 된다.
- **관련**: `AuthCookieProperties.java`, `JwtProperties.java`

### D-008. JWT 시크릿 기본값 제거

- **날짜**: 2026-06 (코드 분석 기반 이슈 수정)
- **상태**: 채택
- **배경**: `application-local.yml`의 `jwt.secret: ${JWT_SECRET:일부기본값}`처럼 기본값이 있으면, 환경변수 설정을 깜빡해도 앱이 "일단 뜬다" — 그 기본값이 그대로 운영에 새어 나가면 토큰 위조가 가능해진다.
- **검토한 대안**:
  1. **기본값 제거(`${JWT_SECRET}`, 미설정 시 기동 실패)** — 설정 누락을 배포 시점에 즉시 발견 / 로컬 최초 세팅 시 한 번은 반드시 값을 채워야 하는 불편.
  2. 기본값 유지 — 로컬 세팅 편함 / 운영 오배포 리스크 상존.
- **결정**: ①. "빨리 실패"가 "조용히 취약하게 뜬다"보다 낫다고 판단.
- **트레이드오프**: 없음에 가까움 — 로컬 개발자는 `.env`나 실행 인자로 한 번만 설정하면 된다.
- **관련**: `application-local.yml`

### D-009. 픽 시 식당 기록 — 기본값(최근접/단일 연결) + 방문 시 덮어쓰기

- **날짜**: 2026-07-06
- **상태**: 채택
- **배경**: `histories.restaurant_id`가 스키마상 "추천된 식당"인데 실제로는 항상 NULL이었다 — "그때 어디 갔었지" 회고 기능의 절반이 데이터 자체가 없어 동작 불가능했다.
- **검토한 대안**:
  1. 픽 시점에 대표 식당(최근접)만 기록 — 구현 단순 / 사용자가 실제로 간 곳과 다를 수 있음.
  2. 방문 처리(`PATCH /history/{id}/visit`) 시에만 restaurantId를 받음 — 정확함(실제 방문지만 기록) / 방문 처리 안 하면 영영 NULL로 남아 데이터가 안 쌓임.
  3. **둘 다: 픽 시 기본값 기록 + 방문 시 덮어쓰기 가능** — 데이터가 지금부터 쌓이면서도, 나중에 정확한 값으로 보정 가능.
- **결정**: ③. 위치 좌표가 있으면 Haversine 최근접 식당, 없으면 연결된 식당이 정확히 1개일 때만 기록(여러 개면 어느 것도 아닌 게 맞다고 보고 NULL 유지 — 틀린 추측보다 없는 게 낫다는 판단).
- **트레이드오프**: 위치 없이 연결 식당이 2개 이상이면 픽 시점 기록은 계속 NULL이다 — 방문 처리로만 채워진다. "정확도 vs 데이터 커버리지"에서 정확도 쪽으로 기운 결정.
- **관련**: `PickService.findNearestRestaurant`, `History.markVisited(Restaurant)`, [ImprovementBacklog.md 2번](ImprovementBacklog.md)

### D-010. `restaurants.kakao_place_id → naver_url` 이행적 종속 — 3NF 위반을 의도적으로 허용

- **날짜**: 설계 단계 (2026-08-15 컬럼명 정정)
- **상태**: 채택 (통제된 비정규화). 컬럼명은 `naver_place_id` → `kakao_place_id`로 바뀌었고([D-028](#d-028-유일성-규칙--닉네임은-중복-불가-식당은-카카오-place-id-기준으로-하나)), 종속 관계 자체와 아래 판단은 그대로 유효하다.
- **배경**: 순수 3NF를 적용하면 `naver_places` 테이블을 분리해 `id → naver_place_id → naver_url`의 이행적 종속을 끊어야 한다.
- **검토한 대안**:
  1. `naver_places` 테이블 분리 — 이론적으로 정규형에 맞음 / `naver_url`이 항상 식당 정보와 함께 조회되는데 매번 JOIN 필요, 조회 성능 손해가 실익보다 큼.
  2. **분리하지 않고 `restaurants`에 유지** — JOIN 없이 바로 조회 / 이론적 3NF 위반.
- **결정**: ②. 조회 패턴(항상 함께 조회), 1:1 관계라 중복 저장 위험이 없다는 점, 네이버 URL이 외부 시스템에 의해 바뀌는 데이터라 오히려 식당 단위로 관리하는 게 갱신 이상 처리에 유리하다는 점을 근거로 비정규화 허용.
- **트레이드오프**: 장소 메타를 여러 식당이 공유하거나 별도로 관리해야 하는 요구사항이 생기면 재검토. 한편 이 컬럼에는 이후 유일성 제약이 붙었으므로(D-028), 분리를 재검토할 때는 그 제약도 함께 옮겨야 한다.
- **관련**: [Planning.md 3.4.3](Planning.md#343-restaurants--이행적-종속-상세-분석)

### D-028. 유일성 규칙 — 닉네임은 중복 불가, 식당은 카카오 place id 기준으로 하나

- **날짜**: 2026-08-15
- **상태**: 채택
- **배경**: 두 자리 모두 유일성 규칙이 없어 문서와 코드가 서로 다른 것을 가정하고 있었다. 닉네임은 `users.nickname`에 아무 제약이 없어 같은 이름이 몇 개든 공존했고, 식당은 같은 가게를 검색해 다시 저장하면 행이 하나 더 생겼다. 후자는 특히 눈에 띄지 않는다 — 목록에 같은 이름이 두 줄 생길 뿐이고, 메뉴 연결은 각각 따로 붙어 흩어진다.
- **검토한 대안**:
  1. **식당 중복 판정을 이름(+주소)으로 한다** — place id가 없는 옛 행도 함께 판정할 수 있다 / **상호가 같은 다른 가게가 실제로 존재한다**. 이름으로 합치면 서로 다른 지점이 하나로 뭉개지고, 한쪽에 붙은 메뉴 연결이 엉뚱한 가게로 딸려 간다. 되돌릴 수 없는 손상이다.
  2. **카카오 place id로만 판정한다.** 장소 검색을 거쳐 저장된 것만 판정 대상이 되고, id가 없는 요청은 비교 근거가 없으므로 그대로 새로 만든다.
  3. 중복 저장을 409로 거절한다 — 구현이 가장 단순 / 사용자는 "이 가게를 목록에 두고 싶다"고 말한 것이고 그 상태는 이미 참이다. 아무 문제도 없는데 오류 화면을 보게 된다.
- **결정**: ② + 중복이면 갖고 있던 식당을 **200으로 돌려준다**(새로 만들었을 때만 201). 201로 뭉뚱그리지 않는 이유는 "새로 저장됐다"와 "이미 있다"가 사용자에게 다른 사실이라 프론트가 안내를 달리 해야 하기 때문이다.
  - 이미 있는 식당은 **덮어쓰지 않는다.** 사용자가 이름·주소를 고쳐 뒀을 수 있는데, 검색 결과를 다시 저장했다는 이유로 그 편집을 되돌리면 안 된다.
  - 유일성 범위는 `(user_id, kakao_place_id)`다. 남이 저장한 가게를 내가 저장하지 못하면 안 된다.
  - 닉네임은 **소셜 로그인에서 거절할 수 없다.** 닉네임은 카카오·구글이 주는 값이고 사용자가 고른 적이 없어, 흔한 이름이라는 이유로 예외를 던지면 그 사람은 로그인 자체를 못 한다. 프로필 제공에 동의하지 않은 사용자는 전원 같은 기본값(`메뉴픽 사용자`)을 받으므로 충돌은 두 번째 사용자부터 곧바로 생긴다. 그래서 소셜 경로는 `NicknameAllocator`가 번호를 붙이고(`홍길동` → `홍길동2`), 사용자가 직접 입력하는 자체 가입만 409로 거절한다.
- **트레이드오프**:
  - `naver_place_id` 컬럼을 `kakao_place_id`로 이름을 바꿨다. 담기는 값은 처음부터 카카오 장소 id였고(장소 검색은 카카오만 쓴다), 유일성 제약이 붙는 컬럼의 이름이 틀린 채로 남으면 나중에 네이버 id를 같은 칸에 섞어 넣는 사고가 난다. 옆의 `naver_url`은 그대로 뒀다 — 표시용 링크라 붙은 불변식이 없다.
  - **soft delete된 식당도 유니크 인덱스의 자리를 차지한다.** 그래서 저장 경로가 "없으면 INSERT"가 아니라 "지워진 게 있으면 되살린다"로 동작해야 한다. 이 조건을 빠뜨리면 지웠던 가게를 다시 저장할 때만 제약 위반이 난다.
  - **탈퇴한 계정도 닉네임을 30일간 점유한다.** 유예기간 안에 돌아오면 쓰던 이름 그대로 복구되어야 하므로 의도한 것이고, 유예가 지나면 하드 삭제 배치가 행을 지우면서 자동으로 풀린다.
  - 마이그레이션은 기존 중복을 **합치지 않는다.** `naver_url`에 남은 카카오 place_url에서 id를 백필하되, 그 결과 같은 사용자가 같은 장소를 두 번 갖고 있던 것이 드러나면 먼저 저장한 행만 id를 유지하고 나머지는 NULL로 되돌린다. 행을 실제로 합치려면 `menu_restaurants`·`histories`의 참조를 옮겨야 하는데, `UNIQUE (menu_id, restaurant_id)` 때문에 같은 메뉴가 양쪽에 연결돼 있으면 옮기다 충돌한다. 스키마 변경이 아니라 데이터 정리 작업이라 분리했다.
  - 서비스 계층의 중복 검사는 **메시지를 위한 것**이고, 실제로 막는 것은 DB 인덱스다. 검사와 저장 사이의 경쟁을 이기는 건 DB뿐이라, 인덱스가 조용히 빠지면 평소에는 멀쩡하고 동시 요청에만 중복이 새는 상태가 된다 — `UniquenessMigrationTest`가 인덱스의 존재와 판정 범위를 고정한다.
- **관련**: `V5__nickname_and_place_uniqueness.sql`, `NicknameAllocator.java`, `RestaurantService.java`, `Restaurant.java`, `UniquenessMigrationTest`, [D-010](#d-010-restaurantsnaver_place_id--naver_url-이행적-종속--3nf-위반을-의도적으로-허용)

### D-027. 운영 Actuator — 관리 포트 분리 + 루프백 바인딩, 그 포트는 무인증

- **날짜**: 2026-08-14
- **상태**: 채택
- **배경**: 운영에서 관측 수단이 사실상 없었다. [D-020](#d-020-actuator-노출--health만-공개-metrics는-인증-필요)이 `metrics`를 "인증 필요"로 열어 뒀지만, 운영 프로파일은 노출 목록을 `health`로 좁혀 놔서 커넥션 풀 고갈·메일 큐 적체·힙을 볼 방법이 아예 없었다. 그렇다고 서비스 포트(8080)에서 `metrics`를 여는 건 다른 문제다 — 그 포트는 리버스 프록시를 거쳐 인터넷에 닿고, `metrics`에는 커넥션 풀 점유·경로별 호출량·힙 사용량이 그대로 들어 있다.
- **검토한 대안**:
  1. 서비스 포트에서 `metrics`를 열고 인증으로 막는다 — 설정 한 줄. 하지만 **운영자가 볼 수 없다**: Access Token은 설계상 브라우저 메모리에만 있고([D-026](#d-026-access-token-저장-위치--메모리-localstoragesessionstorage-대신)) 30분이면 만료돼, 셸에서 꺼내 쓸 수단이 없다. 게다가 역할(Role) 모델이 없어 "인증된 일반 사용자면 누구나" 본다.
  2. **관리 포트를 분리(`management.server.port`)하고, 컨테이너 루프백에만 바인딩(`management.server.address: 127.0.0.1`) + compose에서 publish하지 않는다. 그 포트에 한해 인증을 면제한다.**
  3. Prometheus + 그라파나 스택 — 지표를 시계열로 보는 제대로 된 답이지만, 단일 VM(앱·MySQL·Redis 공유)에 컨테이너를 더 얹는 비용이 지금 규모에 맞지 않는다.
- **결정**: ②. 방어를 "누가 인증했나"가 아니라 **"애초에 닿을 수 없게"**로 옮겼다. 관리 포트에 닿을 수 있는 주체는 이미 컨테이너 안에 있는 사람 — 즉 `docker exec`을 칠 수 있는 운영자뿐이고, 그 사람은 이미 앱 전체를 통제한다. 따라서 거기서 인증을 더 요구해봐야 방어력은 늘지 않고 사용성만 죽는다.
  - 운영자 경로: `docker exec menupick-app curl -s localhost:9090/actuator/metrics`
  - 노출은 `health, metrics`만 유지한다. 관리 포트가 무인증이므로 이 화이트리스트가 유일한 방어선이다 — `env`·`configprops`에는 DB 비밀번호와 JWT 시크릿이 통째로 들어 있다.
  - 부수 효과로 D-020의 트레이드오프가 운영에서 사라진다: 서비스 포트에 actuator 자체가 없으니 일반 사용자는 `metrics`에 닿을 수 없다.
- **트레이드오프**:
  - **`/actuator/health`가 8080에서 사라진다.** 호스트 리버스 프록시가 이 경로를 업스트림 프로브로 쓰고 있었다면 함께 바꿔야 한다. 현재 실제 헬스 신호는 Dockerfile의 `HEALTHCHECK`(컨테이너 안에서 관리 포트를 친다)와 `docker ps`다.
  - 앱과 헬스체크가 `MANAGEMENT_SERVER_PORT` 하나를 공유해 갈릴 수 없게 했지만, 한쪽만 바꾸면 컨테이너가 `unhealthy`로 드러난다(조용히 어긋나지는 않는다).
  - 나중에 같은 compose 망에 Prometheus를 올린다면 `address`를 지워 컨테이너 간 스크레이프를 허용해야 한다. 그때는 무인증 전제가 "같은 망 안"으로 넓어지므로 재검토가 필요하다.
  - 인증 면제를 포트로 판별하는 위험: Boot의 `local.management.port`는 **포트를 분리하지 않으면 서비스 포트 값으로 채워진다**. 이걸 놓치면 local/dev에서 `/api/v1/**` 전체가 permitAll이 된다(실제로 구현 중 이 상태를 만들어 봤고, `TraceIdFilterOrderIntegrationTest`가 401 대신 200을 받아 잡아냈다). `ManagementPortRequestMatcher`는 두 포트가 같으면 무조건 false를 돌려주고, 그 경계는 단위 테스트로 고정돼 있다.
- **관련**: `ManagementPortRequestMatcher.java`, `SecurityConfig.java`, `application-prod.yml`, `Dockerfile`, `docker-compose.prod.yml`, `ManagementPortIntegrationTest`, [Planning.md 7.3](Planning.md#73-로깅-및-모니터링)

### D-029. 부하 테스트 토큰 — 스크립트가 직접 서명해서 만든다

- **날짜**: 2026-08-16
- **상태**: 채택
- **배경**: 부하 테스트가 실행 자체를 못 하고 있었다. 기존 k6 스크립트는 브라우저로 실제 소셜 로그인을 해서 Access Token을 복사해 넣으라고 요구했고, 백로그에도 "OAuth 인가 코드가 실제 리다이렉트를 거쳐야 해 자동화할 수 없다"고 적혀 있었다. 그 판단이 틀렸다는 것이 이 결정의 출발점이다.
- **검토한 대안**:
  1. 기존 방식 유지(수동 복사) — 추가 작업이 없다 / 자동 실행이 불가능하고, Access Token 수명이 30분이라 soak(1시간 이상)는 **중간부터 전부 401**이 된다.
  2. 시드 계정으로 실제 로그인해서 발급받기 — 운영과 같은 경로를 탄다 / 인증 경로는 IP 기준 10회/분으로 막혀 있고, 로그인마다 Argon2 검증(9MiB·수십 ms)이 붙어 **측정하려던 것과 무관한 비용이 결과에 섞인다**.
  3. 테스트 전용 토큰 발급 엔드포인트 추가 — 편하다 / 운영 코드에 인증 우회 경로를 만드는 것이라, 프로파일 가드가 한 번만 어긋나도 그대로 인증 우회 취약점이 된다.
  4. **스크립트가 HS256으로 직접 서명해 만든다.**
- **결정**: ④. 성립 근거는 `JwtAuthenticationFilter`가 **서명·만료·`token_type`만 확인하고 요청마다 DB나 Redis를 조회하지 않는다**는 것이다. 토큰 내용도 `sub = userId`가 전부라, 시크릿과 사용자 id만 있으면 유효한 토큰이 나온다. OAuth 왕복도 메일 인증도 필요 없고, 인증 레이트 리밋과 Argon2 비용이 측정에 섞이지 않는다. 만료 30분 문제는 스크립트 안에서 발급하고 만료 5분 전에 재발급해 해결한다.
- **트레이드오프**:
  - **부하 생성기에 서명 시크릿을 넘긴다.** 운영 시크릿을 이렇게 쓰면 안 된다 — 부하 테스트 전용 환경의 전용 `JWT_SECRET`으로만 돌린다. 운영을 대상으로 재야 한다면 토큰 발급 방식이 아니라 **대상 선정을 다시 생각해야 한다**.
  - 이 조립이 서버와 어긋나면 부하를 걸어야 할 시점에야 401 더미로 드러난다. `K6MintedTokenTest`가 실제 k6 산출물을 서버 파서로 검증해 고정한다.
  - 운영의 실제 로그인 경로(Argon2 비용)는 이 방식으로 측정되지 않는다. 별도 시나리오로 분리했다.
- **관련**: [LoadTestPlan.md 4절](LoadTestPlan.md), `scripts/k6/jwt.js`, `K6MintedTokenTest`

### D-030. 테스트 커버리지 하한 — 목표치가 아니라 래칫

- **날짜**: 2026-08-16
- **상태**: 채택
- **배경**: 커버리지 기준이 없어 테스트가 통째로 빠져도 CI가 통과했다. 백로그 6번이 "커버리지 기준은 별도 과제"로 남겨 둔 항목이다.
- **검토한 대안**:
  1. 기준을 두지 않는다 — 잡음이 없다 / 회귀를 못 잡는다.
  2. 업계 관행값(예: 80%)을 목표로 건다 — 말하기 좋다 / 지금 실측이 그보다 높아 아무것도 막지 못하거나, 반대로 못 미치는 영역에서 **CI가 상시 빨간 상태**가 된다. 그 상태에서는 진짜 회귀도 함께 묻힌다.
  3. **실측보다 조금 낮은 값을 하한으로 걸어 "여기서 더 내려가면 막는다"만 시킨다.**
- **결정**: ③. 실측(LINE 91.8%, BRANCH 79.7%)보다 3~5%p 아래인 LINE 0.88 / BRANCH 0.75로 잡았다. 분기를 함께 보는 이유는 라인만 보면 예외 경로·경계 조건을 한 번도 타지 않고도 수치가 채워지기 때문이다 — 이 프로젝트에서 실제로 위험한 코드는 대부분 그 분기 쪽에 있다. CI의 `test` 잡을 `./gradlew test` → `check`로 바꿔 게이트가 실제로 돌게 했다.
- **트레이드오프**:
  - 하한이 낮아 "커버리지를 올리는" 압력은 없다. 의도한 것이다 — 이 게이트의 목적은 향상이 아니라 **급락 차단**이다.
  - DTO·설정·진입점은 측정에서 제외했다. 검증할 분기가 없는 코드까지 세면 숫자만 오르고 회귀는 그대로 새어 나간다.
  - 실측이 올라가도 하한은 자동으로 따라 오르지 않는다. 큰 폭으로 벌어지면 사람이 올려야 한다.
- **관련**: `build.gradle`의 `jacocoTestCoverageVerification`, `.github/workflows/ci.yml`

### D-025. CORS 설정 신설 — 오리진 화이트리스트 + Credentials 허용

- **날짜**: 2026-08-05
- **상태**: 채택
- **배경**: 백엔드에 CORS 설정이 아예 없었다 — 지금까지는 프론트가 없어 문제가 안 됐지만, Vite 개발 서버(`localhost:5173`)가 백엔드(`localhost:8080`)를 호출하는 순간 브라우저가 막는다. 게다가 Refresh Token이 쿠키(D-002)라 `credentials: include`로 요청해야 하는데, 이건 `Access-Control-Allow-Origin: *`와 함께 쓸 수 없다(스펙상 금지) — 오리진을 명시해야만 한다.
- **검토한 대안**:
  1. **`cors.allowed-origins`를 프로파일별 화이트리스트로 관리, `allowCredentials(true)`** — `local`은 `http://localhost:5173` 고정, `dev`/`prod`는 `FRONTEND_ORIGIN` env로 주입, 값이 없으면(기본) 아무 오리진도 허용 안 함(fail-safe).
  2. 모든 오리진 허용(`*`) — 구현은 가장 간단하지만 credentialed 요청과 함께 쓸 수 없어 애초에 Refresh Token 쿠키 흐름과 양립 불가.
- **결정**: ①. `SecurityConfig`에 `CorsConfigurationSource` 빈 추가.
- **트레이드오프**: 새 프론트 배포지(예: 관리자 페이지 등)가 생기면 그때마다 `FRONTEND_ORIGIN`에 오리진을 추가해야 한다 — 잊으면 조용히 CORS 에러로 막힌다(에러 자체는 브라우저 콘솔에 명확히 남으니 디버깅은 쉬움).
- **관련**: `CorsProperties.java`, `SecurityConfig.java`, [Planning.md 6.2](Planning.md#62-시크릿-관리-원칙)

### D-026. Access Token 저장 위치 — 메모리 (localStorage/sessionStorage 대신)

- **날짜**: 2026-08-05
- **상태**: 채택
- **배경**: Refresh Token은 이미 HttpOnly 쿠키(D-002)로 XSS에서 보호되지만, Access Token을 프론트 어디에 둘지는 별개 문제였다.
- **검토한 대안**:
  1. **JS 모듈 스코프 변수(메모리)에만 보관** — XSS로 실행되는 스크립트가 아니면 접근 불가(다른 취약점과 결합해야 탈취 가능) / 새로고침하면 사라져서, 매번 `/auth/refresh`로 재발급받아야 함.
  2. `localStorage`/`sessionStorage` — 새로고침에도 유지돼 구현이 단순 / XSS 한 방으로 그대로 탈취당함 — Refresh Token을 굳이 쿠키로 뺀 D-002의 취지가 Access Token에서 무너짐.
- **결정**: ①. `AuthContext`가 앱 부팅 시 `refreshAccessToken()`을 한 번 호출해 쿠키 기반으로 세션을 조용히 복원한다.
- **트레이드오프**: 매 새로고침마다 API 호출이 하나 더 나간다(레이턴시 미미, 무시 가능한 수준). 여러 탭을 동시에 열면 탭마다 독립적으로 메모리를 갖는다 — 한 탭에서 로그아웃해도 다른 탭은 Access Token이 만료될 때까지(30분) 살아있을 수 있다. 진짜 즉시 전체 탭 로그아웃이 필요해지면 `BroadcastChannel`류로 탭 간 동기화를 추가해야 한다.
- **관련**: `frontend/src/api/http.ts`, `frontend/src/auth/AuthContext.tsx`
